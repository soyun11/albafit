# rubric-reset-flow.md — 기준 재설정(규칙 다시 편집 → 루브릭 재생성)

> `docs/auth-improvement-plan.md`, `docs/nav-unification.md`와 같은 방식으로 기록한다.

## 왜 만들었나

"기준 관리" 화면(`RubricApproval` 관리 모드)은 이미 만들어진 루브릭의 문구·필수여부만 고칠 수 있었다. 사장님이 애초에 입력했던 규칙 원문 자체를 다시 보고 고쳐서 루브릭을 통째로 재생성하고 싶을 땐 방법이 없었다 — 온보딩 때 썼던 "업종선택→규칙입력→루브릭승인" 3단계는 매장을 처음 만들 때만 도달 가능한 화면이었다.

사용자가 원한 것: "기준 관리" 화면에서 규칙 자체를 다시 편집할 수 있는 진입점이 있으면 좋겠고, StepSidebar의 step1/2/3을 클릭해서 자유롭게 오가며 수정하고 싶다.

## 결정

| 논점 | 결정 | 이유 |
|---|---|---|
| step1(업종)도 실제로 바꿀 수 있게 할까? | **아니오 — 읽기전용** | 업종을 바꾸면 시나리오 자체(카페의 "음료 지연" vs 편의점의 "재고 문의" 등)가 안 맞게 되고, 기존 시나리오·루브릭을 어떻게 처리할지(삭제/보존)까지 새로 설계해야 하는 큰 작업이라 이번 범위에서 제외. 사용자에게 직접 확인받고 결정. |
| 백엔드에 재생성 로직을 새로 만들어야 하나? | **아니오, 이미 있었음** | `POST /:linkKey/rules`는 이미 "이 매장에 쌓인 규칙 원문을 전부 합쳐서 루브릭을 새 버전으로 재생성"하는 로직이었다 — 프론트 진입점만 없었다. |
| 저장된 규칙을 어떻게 다시 보여줄까? | **원문을 카드로 파싱해서 복원** | 규칙 카드는 항상 `"제목: 내용"` 형식으로 직렬화돼 저장되므로(`RulesInput.jsx`의 `handleConfirm`), 그 역변환(`parseRulesText`)으로 안전하게 복원 가능. |

## 구현

### 백엔드 — `GET /api/stores/me/rules` (신규)
`store_rules` 테이블에서 이 매장의 모든 원문을 시간순으로 합쳐서 반환한다. 루브릭 생성 때 실제로 쓰이는 것과 똑같은 조합이라, "지금 루브릭이 근거하는 규칙 전체"를 그대로 보여줄 수 있다.

### `StepSidebar.jsx` — 클릭 가능하게
`onStepClick` prop이 있으면 각 단계를 `<button>`으로 렌더링해서 클릭 시 해당 단계로 이동. prop이 없으면(최초 온보딩) 기존처럼 정적 표시만 — 매장도 없는 단계에서 자유 이동이 오히려 혼란을 준다고 판단해 재설정 흐름에서만 켠다.

### `App.jsx` — `resetMode` 상태
`industry`/`rules`/`rubricManage` 세 화면이 공유하는 `resetMode` boolean과 `resetRawText`(불러온 원문) state를 추가했다.
- `handleResetRules()` — "기준 재설정" 버튼 클릭 시 `GET /me/rules`로 원문을 불러오고 `rules` 화면으로 이동.
- `handleResetStep3()` — StepSidebar의 step3을 누르면 재제출 없이 지금 저장된 루브릭을 그대로 보여줌(`resetMode` 유지).
- `handleResetStepClick(n)` — StepSidebar 클릭을 각 화면으로 매핑하는 공용 디스패처.
- 일반 "기준 관리" AppNav 링크(`handleManageRubrics`)는 항상 `resetMode`를 꺼서, 재설정 도중이었어도 평소 링크로 들어오면 깨끗한 상태로 돌아간다.

### `IndustrySelect.jsx` — 읽기전용 모드
`resetMode`일 때 업종 카드 그리드를 비활성화(선택된 업종만 표시)하고 매뉴얼 입력 카드를 숨긴다. "다음"은 매장 생성 API를 호출하지 않고 바로 규칙 화면으로 넘어간다.

### `RulesInput.jsx` — 저장된 규칙 불러오기
`parseRulesText(rawText)` — `"제목: 내용"` 형식을 두 줄바꿈 기준으로 나눠 카드 배열로 복원하는 함수. `resetMode`일 때 이 함수로 초기 카드를 채우고(라벨은 `SAVED`), 헤딩 문구도 "규칙을 다시 확인해보세요"로 바꾼다. 업종 태그도 하드코딩된 "카페"가 아니라 실제 매장 업종을 보여주도록 고쳤다(온보딩 화면에도 같이 적용되는 부수 수정 — 원래 업종과 무관하게 항상 "카페" 태그가 뜨던 기존 버그였다).

### `RubricApproval.jsx` — `showSteps` / `onStepClick` / `onResetRules`
관리 모드(`onDone` 있음)에서 AppNav에 "기준 재설정" 버튼을 추가했다. `showSteps`가 true면(재설정 흐름 중) StepSidebar를 같이 보여주고 클릭 이동을 허용한다 — 온보딩 모드(`!onDone`)는 항상 보여주되 클릭은 안 되고, 평소 관리 모드는 아예 안 보여주는 기존 동작과 자연스럽게 합쳐진다.

## 검증
- Playwright: 데모 계정으로 로그인 → 기준 관리(StepSidebar 없음, 일반 모드 확인) → "기준 재설정" → 저장된 규칙 4개가 카드로 정확히 복원되는 것 확인 → StepSidebar step1 클릭 → 업종이 읽기전용으로 잠긴 것 확인(다른 업종 클릭 비활성화) → step2로 복귀 → 규칙 하나를 수정("이름을 불러주면 친근하게") → 확정 → **새로 생성된 루브릭에 그 수정 내용이 실제로 반영된 새 채점 기준("고객의 이름을 불러주며 친근하게 응대하는가")이 생긴 것까지 확인** → 3개 모두 재승인 → 대시보드 복귀 → 다시 "기준 관리" 들어가면 StepSidebar 없는 평소 모드로 돌아오는 것 확인. 전 구간 콘솔 에러 0건.
- `npm run lint` 통과.

## 후속 수정 (사용자 실사용 테스트 중 발견)

데모 계정으로 직접 눌러보다가 나온 두 가지를 같이 고쳤다.

### 버그 — STEP1 eyebrow 문구가 재설정 모드에서도 안 바뀜
STEP1의 작은 라벨("eyebrow")이 항상 "매장업종선택 · 매뉴얼입력"으로 고정돼 있었는데, 재설정 모드에서는 매뉴얼 입력 칸 자체를 의도적으로 숨겨놨어서 라벨과 실제 화면이 안 맞았다 — "매뉴얼입력이라는데 그 칸이 안 보인다"는 혼란의 원인. `resetMode`일 때 "매장 정보 · 업종 확인"으로 바꿔서 라벨이 실제로 보여주는 내용과 일치하게 했다.

### 기능 추가 — 매뉴얼 입력을 여러 규칙 카드로 분리
기존엔 STEP1에서 매뉴얼을 통째로 입력하면 STEP2에서 카드 하나("업로드한 매뉴얼 기반 규정")로 뭉뚱그려 보여줬다. 사용자 요청으로 Gemini가 의미 단위로 나눠서 여러 카드로 보여주게 바꿨다.

- `server/src/lib/manualRules.js`(신규) — `splitManualRules({ manualText })`. `rubric.js`와 같은 패턴으로 `responseSchema`(`{ rules: [{title, content}] }`)를 강제해서 JSON으로 안전하게 받는다.
- `POST /api/stores/manual-split`(신규, `stores.js`) — 인증·사장님 role만 확인, storeId는 필요 없음(업종선택 시점엔 매장이 아직 없을 수 있어서).
- `App.jsx`의 `handleIndustryNext`가 매장 생성 직후 매뉴얼이 있으면 이 API를 호출해서 `manualRules` state(배열)에 저장 — 실패해도 온보딩 자체는 막지 않고 빈 배열로 넘어간다.
- `RulesInput.jsx` — 기존 `manualText`(문자열) prop을 `manualRules`(배열) prop으로 교체, 각 항목을 라벨 "매뉴얼 기반"이 붙은 카드로 만든다.

**검증**: 매뉴얼에 "포장 손님에겐 빨대를 요청 시에만 드려요. 마감 30분 전에는 신메뉴 주문을 받지 않아요." 두 문장을 입력 → STEP2에서 "포장 고객 빨대 제공"/"마감 전 신메뉴 주문 제한" 두 카드로 정확히 분리되고 둘 다 "매뉴얼 기반" 라벨이 붙는 것 확인. 재설정 화면 STEP1 eyebrow도 "매장 정보 · 업종 확인"으로 정상 표시되는 것 확인. `npm run lint` 통과.

## 진짜 버그 — 재설정을 쓸 때마다 규칙이 배로 불어남

위 eyebrow 수정을 "버그 고쳤다"고 보고했는데 사용자가 "안 고쳐졌다"고 함 — 다시 확인해보니 훨씬 심각한 다른 버그가 있었다. 데모 계정으로 재설정을 한 번 썼더니 STEP2에 카드가 4개가 아니라 16개(같은 규칙이 4번 반복)로 떠 있었다.

**원인**: `POST /:linkKey/rules`가 매번 "이 매장에 지금까지 쌓인 `store_rules` row 전부"를 합쳐서 루브릭을 생성했다. 온보딩처럼 평생 한 번만 제출하는 흐름에선 문제가 없었지만, "기준 재설정"이 생기면서 같은 매장에 여러 번 제출하는 상황이 실제로 생겼고, 그때마다:
1. `GET /me/rules`가 지금까지 쌓인 전부를 합쳐서 카드로 보여줌
2. 그 카드 전부(=이미 합쳐진 과거 내용 포함)를 다시 제출
3. 그게 새 row로 또 쌓이고, 다음 조회 때 또 전부 합쳐짐

→ 제출할 때마다 내용이 두 배로 불어나는 구조였다(4 → 8 → 16 ...).

**수정**: `POST /:linkKey/rules`는 이제 방금 이 요청으로 저장한 `storeRule.rawText` 하나만 루브릭 생성에 쓴다(과거 row를 다시 합치지 않음). `GET /me/rules`도 전체 합산 대신 가장 최근 row 하나만 반환하도록 바꿨다. 과거 row들은 삭제하지 않고 DB엔 그대로 남는다(원문 보존 원칙 유지) — 다만 "지금 활성화된 규칙"으로는 더 이상 안 쓰일 뿐이다. 온보딩처럼 애초에 한 번만 제출하는 경우엔 "최신 row"와 "전부 합친 것"이 결과가 똑같아서 이 변경으로 인한 동작 차이가 없다.

데모 계정에 이미 쌓여있던 중복 row 2개는 정리했다(원본 row 하나만 남김, Gemini는 다시 호출하지 않았고 기존 승인된 루브릭은 그대로 유효).

**검증**: 데모 계정으로 재설정 진입 → 카드 4개(정상) 확인 → 수정 없이 그대로 확정·재생성·승인 → 다시 재설정 진입 → 여전히 카드 4개(중복 없음, 회귀 테스트 통과). `npm run lint` 통과.

## 세 번째 라운드 — "매뉴얼입력했던 게 다시 안 뜬다"

앞의 두 수정(eyebrow 문구, 중복 누적 버그) 다음에도 사용자가 스크린샷과 함께 같은 얘기를 반복 — 실제로 가리킨 건 STEP1(매장 업종) 화면 자체였다. 재설정 모드에서 "업종은 못 바꾼다"는 이유로 매뉴얼 입력 칸까지 통째로 숨겨놨었는데, 사용자가 원한 건 **업종은 못 바꿔도 매뉴얼 입력 칸은 계속 쓸 수 있어야 한다**는 것이었다.

기존 구조에서 매뉴얼 텍스트는 한 번 제출되면 STEP2의 일반 규칙 카드로 흡수되고 "이게 매뉴얼에서 온 것"이라는 표시가 DB엔 남지 않는다 — 그래서 "저번에 입력한 매뉴얼 원문"을 그대로 복원하는 건 불가능하다. 대신 STEP1에 매뉴얼 입력 칸을 다시 노출해서, **새로 매뉴얼을 적으면** 온보딩 때와 똑같이 Gemini가 여러 카드로 쪼개 STEP2로 넘겨주게 만들었다. STEP2에 진입하면 "그동안 저장된 규칙"(SAVED 라벨)과 "이번에 새로 적은 매뉴얼"(매뉴얼 기반 라벨)이 함께 보인다.

- `IndustrySelect.jsx` — `resetMode`에서도 매뉴얼 입력 카드는 그대로 두고(업종 힌트 박스만 숨김), 안내 문구만 "새로 적은 내용을 카드로 추가해드려요"로 바꿈.
- `App.jsx` — 매뉴얼 분리 호출을 `splitAndSetManualRules(text)` 공용 함수로 뽑아서 온보딩(`handleIndustryNext`)과 재설정(`handleResetIndustryNext`) 둘 다 재사용. 재설정 진입(`handleResetRules`) 시점엔 이전에 남아있을 수 있는 `manualRules`를 비워서, 재설정할 때마다 새로 입력한 것만 반영되게 함.
- `RulesInput.jsx` — `resetMode`일 때도 `manualRules`(새 매뉴얼 분리 결과)를 `parseRulesText(initialRawText)`(저장된 이력) 앞에 붙여서 같이 보여줌.

**검증**: 데모 계정 재설정 → STEP1에 매뉴얼 입력 칸이 다시 보이는 것 확인 → "단골 손님은 이름을 기억해서 불러드려요. 시즌 한정 메뉴는 매장 입구에 안내판으로 먼저 소개해요." 입력 → STEP2에서 저장된 규칙 4개(SAVED) + 새로 분리된 매뉴얼 카드 2개("단골 손님 응대"/"시즌 한정 메뉴 홍보", 매뉴얼 기반)가 합쳐서 6개로 정확히 뜨는 것 확인. 콘솔 에러 0건, `npm run lint` 통과.

## 네 번째 라운드 — 카드별 출처(라벨) 보존

"매뉴얼입력했던 게 다시 안 뜨는 이유"를 설명하면서 "SAVED로 뭉뚱그려지는 게 기술적으로 불가능해서가 아니라, 애초에 카드별 출처 정보를 저장 안 해서"라고 답했다. 사용자가 "그럼 만들어줘"라고 해서, 앞으로의 제출부터는 카드별 라벨을 실제로 저장하도록 구조를 바꿨다.

- `store_rules`에 `items Json?` 컬럼 추가(마이그레이션 `20260715075203_add_store_rule_items`) — 이 제출에 담긴 카드들을 `[{label, title, example, mascot}]` 그대로 저장한다. `rawText`(Gemini 프롬프트·감사용 순수 텍스트)는 그대로 두고 건드리지 않았다 — 라벨 태그가 채점 기준 생성에 노이즈를 주지 않게.
- `POST /:linkKey/rules`가 `items`를 optional로 받아 저장, `GET /me/rules`가 최신 row의 `items`도 같이 반환.
- `RulesInput.jsx`의 `handleConfirm`이 켜진 카드 전부를 `items`로도 같이 보냄. 재설정 화면 진입 시 `initialItems`가 있으면(이 컬럼이 생긴 뒤 저장된 제출) 그걸로 카드를 바로 복원(원래 라벨 그대로), 없으면(과거 데이터) `parseRulesText` 폴백(SAVED).
