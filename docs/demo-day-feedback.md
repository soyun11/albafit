# demo-day-feedback.md — 데모데이(2026-07-31) 피드백 정리 + 다음 버전 후보

> 부스 전시(2026-07-31) 중 여러 멘토·참가자로부터 받은 질문·피드백을 정리한다. 4주 챌린지는 여기서 마무리하고, 실제 서비스로 업데이트할 때 참고할 결정 기록으로 남긴다. 이번 챌린지의 이슈 트래커(soyun11/hub)는 이미 전부 정리된 상태라, 여기 적힌 항목들은 바로 이슈화하지 않고 다음 버전 작업을 시작할 때 `task-planner`로 다시 쪼개 이슈화한다.

## 1. 이미 구현되어 있던 것 (정확히 답변함)

**박상현 멘토(2주차 멘토링 담당)** — "LLM API 호출 비용을 줄이려고 노력했는가?"

- 현장 답변: 비슷한 매뉴얼일 경우 80% 이상 유사도면 그 매뉴얼로 채택하도록 설계했다.
- 실제로 `server/src/lib/rubricReuse.js`의 `SIMILARITY_THRESHOLD = 0.8`이 이 기능이다 — 같은 업종의 승인된 루브릭 배치 중 자카드 유사도 0.8 이상인 게 있으면 Gemini 재호출 없이 그대로 복제한다([`docs/rubric-reuse.md`](./rubric-reuse.md)). 즉석 답변이 실제 구현과 정확히 일치했다.

## 4. 매뉴얼 원문 재사용 구조 (멘토 피드백 후속 분석, DM)

**김웅일 멘토(1주차 멘토링 담당)** — 부스 현장이 아니라 이후 DM으로 온 후속 질문. "알바 답을 채점·가이드할 때 LLM한테 항상 매뉴얼 전체를 넘긴다고 생각했는데, 매뉴얼이 방대해지면 관련 없는 내용이 많이 전달돼서 비용·정확도 이슈가 있을 것 같다. 관련 있는 데이터만 골라서 넘기는 방법이 고려됐을까?"

### 확인 결과 — 실제로 이런 구조였다

- **채점(`evaluator.js`의 `evaluateTurn`)은 매뉴얼 원문을 아예 받지 않는다.** 이미 생성된 루브릭(`criteria`, 항목 몇 개짜리 체크리스트)만 본다 — 이 부분은 걱정하신 구조가 아니었다.
- **문제는 시나리오별 루브릭을 만드는 단계(`rubric.js`의 `generateRubric`)였다.** `server/src/routes/stores.js`가 시나리오 N개에 대해 각각 `generateRubric({ rawRulesText: combinedRulesText, ... })`을 호출하는데, 이때 `rawRulesText`(매뉴얼 원문 전체)가 매번 그대로 다시 들어간다 — 시나리오 3개면 원문 전체가 3번 반복 전송된다.

### 비용 문제와 정확도 문제는 원인이 다르다 — 해결책도 나뉜다

| 문제 | 원인 | 해결책 |
|---|---|---|
| 비용 | 시나리오 개수만큼 같은 원문을 반복 전송 (호출 횟수 문제) | **배치화** — 시나리오 N개를 한 프롬프트에 묶어 1번만 호출. `docs/ai-usage-and-cost-review.md` 4절에 이미 있던 안. 원문 반복 전송은 없어지지만, 한 번의 호출 안에 원문 전체가 들어가는 건 그대로라 정확도 문제는 안 풀림 |
| 정확도 | 시나리오 하나 처리하는데 무관한 규정까지 매번 같이 보여져서 모델이 헷갈릴 여지가 생김 (호출 내용물 문제) | **관련 카드만 필터링** — `store_rules.items`(카드별 title+content, 이미 저장돼 있지만 지금은 안 쓰임)에서 이 시나리오와 관련 있는 카드만 골라 `rawRulesText` 대신 그것만 전달. 유사도 계산은 새로 안 만들고 `rubricReuse.js`의 `computeTextSimilarity`(자카드 유사도)를 재사용. 결과적으로 전송량 자체가 줄어 비용도 같이 개선됨(단, 역은 성립 안 함 — 배치화만으론 정확도가 안 좋아짐) |

### 부수 발견 — 매뉴얼 텍스트 길이 제한이 아예 없음

이 논의 중 직접 코드로 확인: `scenarioProposer.js`의 `scenarios.slice(0, 20)`처럼 **시나리오 개수는 이미 상한(20개)이 있는데**, `stores.js`의 `rawText`/`manualText` 검증은 `trim().length === 0`(비어있는지)만 확인하고 **상한 길이 체크가 전혀 없다.** 이메일 필드(`length > 255`)에는 있는 상한 검사가 매뉴얼 텍스트에는 빠져있다. 매뉴얼이 아주 길어지면 ① 비용이 무한정 늘고 ② 모델의 컨텍스트 한계를 넘어 호출 자체가 실패할 수 있다 — 시나리오 개수 제한과 짝을 이루는 텍스트 길이 상한을 추가해야 한다.

### 다음 버전에서 할 일 (우선순위 순)

1. `rawText`/`manualText`에 최대 길이 검증 추가 (이메일 필드 패턴과 동일하게)
2. 관련 카드 필터링(`rubricReuse.js`의 유사도 함수 재사용) — 정확도 문제의 근본 해결
3. 시나리오 배치화 — 비용 문제 해결, 2번과 별개로 병행 가능
