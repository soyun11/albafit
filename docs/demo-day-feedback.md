# demo-day-feedback.md — 데모데이(2026-07-31) 피드백 정리 + 다음 버전 후보

> 부스 전시(2026-07-31) 중 여러 멘토·참가자로부터 받은 질문·피드백을 정리한다. 4주 챌린지는 여기서 마무리하고, 실제 서비스로 업데이트할 때 참고할 결정 기록으로 남긴다. 이번 챌린지의 이슈 트래커(soyun11/hub)는 이미 전부 정리된 상태라, 여기 적힌 항목들은 바로 이슈화하지 않고 다음 버전 작업을 시작할 때 `task-planner`로 다시 쪼개 이슈화한다.

## 1. 이미 구현되어 있던 것 (정확히 답변함)

**박상현 멘토(2주차 멘토링 담당)** — "LLM API 호출 비용을 줄이려고 노력했는가?"

- 현장 답변: 비슷한 매뉴얼일 경우 80% 이상 유사도면 그 매뉴얼로 채택하도록 설계했다.
- 실제로 `server/src/lib/rubricReuse.js`의 `SIMILARITY_THRESHOLD = 0.8`이 이 기능이다 — 같은 업종의 승인된 루브릭 배치 중 자카드 유사도 0.8 이상인 게 있으면 Gemini 재호출 없이 그대로 복제한다([`docs/rubric-reuse.md`](./rubric-reuse.md)). 즉석 답변이 실제 구현과 정확히 일치했다.

## 2. 검증이 필요한 것 (숙제로 남음)

| 질문 출처 | 질문 | 지금 상태 | 해야 할 일 |
|---|---|---|---|
| 다른 멘토 | API 비용 계산/최적화를 해봤는가 | 안 함 — 현장에서 "추후에 하겠다"고 답변 | [`docs/ai-usage-and-cost-review.md`](./ai-usage-and-cost-review.md) 4절에 이미 "호출 횟수/토큰 로깅 먼저"라는 우선순위가 적혀있다. 다음 버전에서 이 로깅부터 넣고, 실측 데이터로 비용을 계산해 최적화 여부를 판단한다 |
| 다른 멘토 | 매뉴얼→시나리오 변환 시 Gemini 3.5-flash가 이상한 시나리오를 만든 적 있는가 | 현장에서 "아마 없었다"고 답했지만, 실제로 점검한 적은 없음 | 지금 캘리브레이션([`docs/evaluation-calibration.md`](./evaluation-calibration.md))은 **평가(채점)** 결과만 사람이 검토하는 구조다 — **시나리오 생성** 결과에 대한 검토 지점은 없다. 시나리오 제안 결과를 사람이 확인할 수 있는 화면을 마련하거나, 최소한 회귀 셋(`server/eval/`)에 시나리오 생성 케이스를 추가해 확인이 필요하다 |
| 다른 멘토 | 여러 LLM 호출에 동일 시스템 프롬프트를 쓰는 게 캐싱을 의도한 거냐 | 현장에서 얼버무림 | 프롬프트 캐싱이 정확히 뭘 뜻하는지(반복되는 입력 토큰을 재사용해 비용·지연을 줄이는 것)부터 조사하고, 지금 구조(호출마다 같은 `SYSTEM_PROMPT` 문자열을 그대로 재사용)가 실제로 그 이득을 보고 있는지, 보려면 뭐가 더 필요한지(예: Gemini/OpenAI의 프롬프트 캐싱 API를 명시적으로 써야 하는지)를 확인해 답을 구체화한다 |

## 3. 다음 버전 아이디어

| 아이디어 | 제안자 | 메모 |
|---|---|---|
| 매장 매뉴얼 사진/PDF 업로드 + OCR | 본인 | 이미 [`docs/plan.md`](./plan.md) 7절 "v1.5"에 있던 계획("매뉴얼 사진 → 규칙 초안, Claude 비전 입력")과 같은 방향 — 새 아이디어라기보다 기존 계획의 재확인 |
| 음성 입력(STT) 도입 | 발표한 참가자(서울대생) | `docs/plan.md` 5-4에서 "STT가 새 할루시네이션 소스가 되어 평가 신뢰성을 흔든다"는 이유로 v1에서 의도적으로 제외한 결정과 정면으로 배치된다. 도입하려면 이 트레이드오프(응대 내용 학습 vs 톤 학습, 평가 신뢰성 리스크)를 다시 판단해야 한다 |
| 대안 모델 검토(비용) | 참가 학생 1명 | "코덱스 루나" 등 가격이 나뉜 모델을 언급 — 정확히 어떤 서비스인지 재확인이 먼저 필요하다. 확인되면 `docs/ai-usage-and-cost-review.md`의 "모델 티어링 재점검"(4절 5번) 항목과 같이 검토 |
| 매장 구조 게임화 (편의점 재고 위치 학습 등) | 참가 학생 1명 | 지금 서비스는 "응대 대화" 훈련만 다룬다 — 매장 레이아웃·재고 위치처럼 대화가 아닌 공간/지식 학습은 완전히 다른 기능(미니게임 등)이 필요한, 별개의 새 트랙에 가깝다 |
| 플랫폼 분리 — 사장님 웹 / 알바 앱 | 본인 | 사장님은 설정 작업(규칙 입력·승인·리포트 확인)이라 데스크톱 웹이 자연스럽고, 알바는 실전 대화 연습이라 모바일 앱이 더 맞을 수 있다. 지금은 반응형 웹 하나로 두 역할을 다 커버 중 |
