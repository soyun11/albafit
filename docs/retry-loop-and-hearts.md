# retry-loop-and-hearts.md — 재입력 루프 + 하트(생명) 시스템

> `docs/rubric-reset-flow.md`와 같은 방식으로 기록한다.

## 배경

훈련 세션의 턴 루프(손님→답변→평가→다음 손님)는 이미 있었지만, 필수 기준을 못 채운 답변도 그냥 다음 턴으로 넘어갔다 — 알바가 그 자리에서 다시 답할 기회가 없었다. task-planner로 계획을 짠 뒤, 실제로 만들면서 사용자가 직접 눌러보고 지적한 문제들을 그때그때 고치며 최종 형태가 여러 번 바뀌었다.

## 1. 재입력 루프

- 클라이언트는 "이건 재입력이에요"라고 따로 알려주지 않는다. 서버(`server/src/routes/sessions.js`)가 이 세션의 마지막 row가 `passed: false`면 이번 제출을 그 턴의 재입력으로 본다.
- 재입력이면 클라이언트가 보낸 `customerMessage` 대신 직전 시도의 손님 질문을 그대로 쓴다 — "같은 질문에 다시 답한다"는 전제를 서버가 직접 보장한다.
- `evaluateTurn()`(`server/src/lib/evaluator.js`)에 `previouslyMetItems`를 추가해, 같은 턴 안 이전 시도에서 이미 충족한 기준을 이번 채점에서 다시 미충족으로 판단하지 않는다. LLM 판단만 믿지 않고 코드에서 강제로 union한다.

## 2. 손님 에이전트가 재입력 대화를 다 기억하도록 수정

재입력으로 답이 여러 번(예: "죄송합니다" → "10분 정도 걸려요" → "리필도 됩니다") 나뉘면, 처음엔 손님 에이전트에게 **최종 시도 하나만** 넘겨서 앞의 답변들을 손님이 못 들은 것처럼 다시 캐묻는 문제가 있었다(사용자가 실제로 화면에서 발견). `pickFinalAttempts`(리포트 집계용, 최종 결론 하나만)와 `buildConversationHistory`(손님 에이전트용, 그 턴 안의 시도 전부)를 분리해서 해결했다 — `server/src/lib/sessionTurns.js`.

## 3. 조기 완료 — 기준을 다 채우면 남은 턴을 억지로 안 채움

기존엔 시나리오당 무조건 3턴을 다 채워야 끝났다. 세션 전체(턴을 넘나들며)에서 루브릭 필수 기준을 한 번이라도 다 충족했으면(`allCriteriaMet`), 남은 턴을 진행하지 않고 바로 완료 처리한다. 프론트(`TrainingSession.jsx`)는 완료되면 축하 배너를 보여주고 — 사용자 요청으로 **자동 전환이 아니라 "결과 화면으로 넘어가기" 버튼**을 눌러야 넘어가게 했다.

## 4. 하트(생명) 시스템 — 재입력 횟수를 세션 전체 기준으로

원래 재입력은 턴마다 최대 2회(총 3회 시도)로 제한했는데, 사용자가 화면에서 "재입력 턴마다 카운트가 리셋되는 게 헷갈린다"고 지적해서 세션 전체 기준으로 바꿨다.

- **하트 총량** = 이 시나리오 루브릭 기준 개수 × 2 (`HEARTS_PER_CRITERION`, `server/src/lib/sessionTurns.js`).
- **차감 규칙**: 이 답변이 "새로 충족시킨 기준이 하나도 없을 때"만 하트 1개가 깎인다. 일부라도 새로 채우면 안 깎인다 — `countOffTopicAttempts()`가 시간순으로 다시 훑으면서 각 시도가 그 시점까지 누적된 기준 집합에 뭔가 새로 보탰는지를 판단한다.
- **하트가 0이 되면 그 즉시 훈련 전체가 끝난다** — 통과 여부와 무관하게. 재입력 횟수 제한(턴별 상한)은 삭제했다: 이제 재입력은 하트가 남아있는 한 계속 가능하다.
- 하트 개수는 매번 새로 계산하지 않고 `computeHearts(sessionTurns)`로 매 요청마다 그 세션의 `sessionTurns`에서 다시 계산한다 — 별도 DB 컬럼을 추가하지 않았다(스키마 변경 없음). "기준 재설정"으로 나중에 루브릭이 바뀌어도 그 세션이 실제로 채점받은 기준 개수(그 세션의 `evaluation.metItems`에 등장한 서로 다른 기준 수)를 그대로 쓰기 때문에 흔들리지 않는다.

## 5. 점수 계산 방식 변경 — 기준 충족률 → 하트 잔량 비율

기존엔 "기준 충족률"(충족한 기준 수 / 전체 기준 수)로 점수를 매겼는데, 재입력으로 결국 다 맞히면 몇 번을 틀렸든 항상 100점이 나오는 문제가 있었다. 점수를 **남은 하트 / 전체 하트**로 바꿨다 — 실제로 몇 번 헤맸는지가 반영된다.

- `server/src/routes/stores.js`의 `/me/staff-report`(목록)와 `/me/staff/:staffId/latest-report`(상세) 둘 다 같은 `computeHearts()`를 써서 점수 계산식을 통일했다(목록/상세 점수 불일치를 다시 만들지 않기 위해 — `docs/staff-report-and-rubric-fix.md` 2절과 같은 원칙).
- `FeedbackReport.jsx`의 "교정 피드백" 건수도 원래 "마지막에 안 채워진 기준 수"였는데, 재입력으로 결국 다 채우면 몇 번을 틀렸든 항상 0건으로 뜨는 문제가 있어서 **깎인 하트 수**(`maxHearts - heartsRemaining`)로 바꿨다 — 이게 실제로 "몇 번 교정받았는지"를 정확히 센다.

## 6. 평가 AI가 짧은 답변을 너무 엄격하게 채점하던 문제

"죄송합니다"라고만 답해도 그 직전에 손님이 "늦다"고 말했으면 지연에 대한 사과로 봐야 하는데, 채점 AI가 루브릭의 "좋은 예시" 문장만큼 구체적이지 않다는 이유로 미충족 처리하고 있었다(사용자가 실제로 발견 — 체크리스트는 그대로인데 하트만 깎이는 것으로 나타났다). `evaluator.js`의 `SYSTEM_PROMPT`에 "좋은 예/나쁜 예는 참고용일 뿐, 맥락상 그 기준의 핵심 행동을 했으면 met: true로 판단하라"는 지침을 추가해서 고쳤다.

## 알려진 한계 / 오늘 범위 밖

- 하트 계산(`countOffTopicAttempts`)은 매 요청마다 `sessionTurns` 전체를 다시 순회한다 — 세션이 아주 길어지면(지금 구조에서는 사실상 안 생기지만) 비용이 늘 수 있다. 지금 규모에선 문제없다.
- 게스트 체험(`guest.js`)에는 재입력/하트를 넣지 않았다 — DB 없는 stateless 플로우라 "서버가 DB 상태로 판별" 전략이 안 맞는다.

## 검증

- curl로 직접 여러 시나리오를 재현: 완전히 엉뚱한 답(하트 차감 확인), 부분 진행 답(하트 안 깎임 확인), 하트 6개를 정확히 소진시켜 즉시 종료되는지 확인, 재입력을 여러 번 나눠 답해도 손님이 이미 들은 내용을 다시 안 캐묻는지 확인.
- Playwright로 실제 브라우저 로그인 → 훈련 시작 → 답변 제출 → 하트 UI·진행바·축하 배너·자동완료 방지(버튼 클릭 필요)까지 화면으로 확인.
- 사장님 계정으로 `/me/staff-report`, `/me/staff/:staffId/latest-report` 조회해 목록·상세 점수가 하트 기준으로 서로 일치하는지 확인.
- `npm run lint` 통과.
