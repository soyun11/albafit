# staff-account-recovery.md — 알바 계정 정보를 잃어버렸을 때 복구

> `docs/rubric-reuse.md`와 같은 방식으로 기록한다. 근거: 사용자가 대시보드 통합 작업 중 지적한 실사용 시나리오, 2026-07-22.

## 왜 만들었나

사장님이 알바 계정을 만들 때(`POST /api/stores/me/staff`) 이메일과 초기 비밀번호를 직접 정해서 알바에게 알려주는 구조다. 그런데 지금은:
- 대시보드 알바 목록에 **이메일이 안 보인다** — `GET /me/staff-report` 응답에 이메일 필드 자체가 없다. "이번에 만든 계정" 목록(세션 로컬)에서만 잠깐 보이고 새로고침하면 사라진다.
- 비밀번호를 사장님이 잊어버리거나 알바에게 잘못 전달했을 때, **다시 확인하거나 바꿀 방법이 전혀 없다.** 알바 본인이 로그인해서 바꾸는 기능(`PATCH /api/auth/password`)은 있지만, 애초에 로그인이 안 되면 그 기능 자체에 도달을 못 한다.

즉 사장님이 알바 계정 정보를 잃어버리면 그 계정은 사실상 복구 불가능한 상태가 된다.

## 결정

| 논점 | 결정 | 이유 |
|---|---|---|
| 이메일 확인 | 대시보드 알바 목록 표에 이메일을 이름 아래 작은 글씨로 항상 표시 | 언제든 다시 확인 가능해야 한다. 새 컬럼 대신 이름 셀 안에 부가 정보로 넣어 표 폭을 늘리지 않는다. |
| 비밀번호 복구 | 알바 본인 확인 없이 **사장님이 새 비밀번호를 직접 정해서 덮어쓸 수 있게** — 계정 생성 때와 같은 방식(사장님이 임의의 비밀번호를 정함) | 이메일 인증 기반 "비밀번호 재설정 링크" 같은 흐름은 이 서비스 규모에 비해 과하다. 애초에 알바 계정을 사장님이 직접 만드는 구조(자기 이메일 인증 없음)라, 복구도 같은 신뢰 모델(사장님이 관리자 권한으로 직접 설정)을 따르는 게 일관적이다. |
| UI 위치 | 새 화면을 만들지 않고 **대시보드 알바 목록 표의 각 행에 "비밀번호 재설정" 인라인 액션**으로 | 오늘 알바 관리 기능을 전부 대시보드로 모으기로 한 결정과 같은 방향 — 별도 화면을 또 만들면 그 결정과 어긋난다. 클릭하면 행 바로 아래에 비밀번호 입력 한 칸 + 저장 버튼이 펼쳐지는 가벼운 인라인 폼. |
| 인증 | 기존 계정 생성과 동일하게 `requireRole('owner')` + 소유권 확인(그 알바가 내 매장 소속인지) | `latest-report`의 소유권 확인과 같은 패턴 재사용. |

## 구현·검증

### 구현
- `server/src/routes/stores.js` — `GET /me/staff-report` 응답의 `staff[]`에 `email` 추가. `PATCH /me/staff/:staffId/password`(owner 전용) 신규 — 소유권 확인(`storeId`+`role==='staff'`) 후 `hashPassword`로 덮어씀.
- `src/components/OwnerDashboard.jsx` — 이름 셀에 이메일 표시. 행마다 "비밀번호 재설정" 인라인 링크 → 클릭 시 그 행 아래 입력칸+저장 버튼이 펼쳐짐(`Fragment`로 감싸 조건부 렌더링). 저장 성공 시 "변경 완료" 표시 후 2초 뒤 원상복귀. 버튼 클릭은 전부 `stopPropagation`으로 행의 "리포트 보기" 클릭과 안 겹치게 분리.
- `src/components/OwnerDashboard.css` — `.staff-email`, `.reset-password-row`/`.reset-password-form`, `.btn-primary-sm`(재도입) 추가.
- 서버 테스트 70개 + 루트 12개 + lint + build 통과.

### 브라우저 확인 (`claude-in-chrome`, 기존 테스트 계정)
- 대시보드 알바 목록에 이메일이 이름 아래 항상 표시됨.
- "비밀번호 재설정" 클릭 → 행 클릭(리포트 이동)은 안 트리거되고 인라인 폼만 펼쳐짐 확인.
- 새 비밀번호 입력·저장 → "변경 완료" 표시, 폼 자동 접힘.
- **실제 로그인으로 검증**: `curl -X POST /api/auth/login`에 방금 설정한 새 비밀번호로 호출 → 정상 로그인 확인(기존 비밀번호는 더 이상 안 통함, 덮어쓰기가 실제로 적용됨).
- 콘솔 에러 없음.
