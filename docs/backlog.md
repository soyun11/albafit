## 1. 백로그란?

- **정의**: 해야 할 일을 전부 모아둔 하나의 목록. "언젠가 할 일"까지 다 적어두고, 그중 우선순위 높은 것부터 꺼내 쓴다.
- **왜 필요한가**: 할 일이 머릿속이나 대화에만 있으면 놓치거나 순서가 흔들린다. 한곳에 모아두면 "지금 뭐부터 해야 하지?"를 매번 고민하지 않아도 된다.
- **어떻게 생겼나**: Task 이름 + 우선순위 + 상태(백로그/진행중/완료) + 어느 주차 것인지, 이 정도 컬럼만 있는 단순한 표. 화면 스펙처럼 세세하게 쓰지 않는다 — 그건 checklist.md 같은 별도 문서 몫.
- **어떻게 관리하나**: 지금은 이 마크다운 파일로 관리하고, 이후 Notion 데이터베이스로 그대로 옮긴다. 매주 시작할 때 이번 주에 할 항목을 위쪽으로 올리고, 끝나면 상태를 "완료"로 바꾼다.

---

## 2. 우선순위 · 상태 표기 규칙

| 표기 | 의미 |
|---|---|
| **필수** | 없으면 서비스가 성립 안 함 (코어: A 대화 + B 평가) |
| **중요** | 있어야 쓸 만해짐 (규칙 입력, 신뢰성, 배포) |
| **여유** | 시간 남으면 (리포트, 자동화, 디테일) |

상태는 `백로그`(아직 시작 전) → `진행중` → `완료` 세 가지만 쓴다.

- **MCP 도입 보류** — 현재 서비스는 사장님/알바가 직접 쓰는 웹서비스 구조라, 외부 AI 툴(Claude·Cursor 등)이 이 서비스를 호출할 니즈가 없다는 의견. 기존 계획(코어+배포가 끝나기 전엔 MCP에 손대지 않는다, plan.md 5-6)과 이미 일치 — 조기 도입하지 않기로 재확인.
- **사장님 인터뷰/설문으로 문제 검증** — 사업화가 아니라 포트폴리오 목적의 4주 챌린지이므로, 검증보다 기능 개발을 우선하는 게 맞다는 의견. 다만 시간이 남으면 가볍게 진행할 수 있도록 Task 표에 "병행" 트랙으로 추가 (특정 주차에 고정하지 않음, 여유 우선순위).
- **AI 평가 결과 교차검증 루프** — 평가 에이전트(Claude Sonnet 5)의 채점 결과를 GPT 등 다른 모델로 한 번 더 검증하는 방법 제안받음. 기존 3주차 "평가 에이전트 캘리브레이션(사장님 검토)"이 사람에 의한 검증이라면, 이건 자동화된 모델 간 교차검증 — 두 방식을 병행하는 방향으로 3주차 Task에 별도 항목으로 추가.

## 7. 멘토링 반영 (2026-07-20)

멘토링(멘토: 박상현, 배송상품정보개발)에서 받은 피드백 중 이 프로젝트에 해당하는 액션 아이템을 반영한다. (커리어·면접 준비 관련 피드백은 프로젝트 범위가 아니라 이 문서에는 안 옮김.)

- **"LLM을 꼭 써야 하는가"를 호출 지점마다 재검토** — AI 호출량이 늘수록 비용도 늘고, input 대비 output을 보장하기 어렵다는 지적. 지금 AI 호출 지점(손님 대화·채점·규칙→루브릭 변환·시나리오 제안·매뉴얼 자동분리) 중 매뉴얼 자동분리(`manualRules.js`)는 규칙 기반 파싱으로 대체 가능한지, 채점(`evaluator.js`)의 항목별 met/unmet 판단 일부는 임베딩 유사도 매칭으로 대체 가능한지 검토 과제로 추가. 시나리오/루브릭 생성은 매장마다 규칙이 다르다는 게 서비스 핵심 가치라 AI 유지 근거가 있다고 판단, 재검토 대상에서 제외.
- **루브릭 재사용성** — 업종·규칙이 비슷한 매장끼리 루브릭 템플릿을 캐싱/공유하면 Gemini 호출 자체를 줄일 수 있다는 제안. 지금은 매장마다 매번 새로 생성하는 구조라 검토 과제로 추가.
- **"이게 진짜 필요한 기능인가" 자체 점검** — 알바 훈련 시간 단축·매출 기여를 실제로 증명할 수 있는지 스스로 물어봐야 한다는 의견. 4주 챌린지 특성상 지금 정량 검증은 어렵지만, 최소한 발표에서 이 질문을 스스로 던지고 있다는 점을 짚고 넘어가기로 함 — 별도 Task는 아니고 기존 "사장님 인터뷰/설문(문제 검증)" 병행 트랙과 같은 맥락으로 흡수.

> 3주차 데일리 미션(학습 목표: DB 연동 완성, 새 기능 AI 설계+이슈 단위 개발, 아키텍처 시각화, 테스트/TDD)을 기존 3주차 계획(checklist.md)과 대조해 겹치는 것·새로 추가해야 하는 것을 나눴다.

**이미 충족됨** (미션 요구사항과 기존 작업이 겹침)
- DB 연동 완성 — Supabase에 실제 데이터가 저장/조회되는 구조는 1~2주차부터 이미 완성, `feature-verifier`로 오늘 재확인함.
- 코드 검증 Agent를 만들어 개발한 기능에 활용 — `feature-verifier`(`.claude/agents/feature-verifier.md`) 제작 후 시나리오 생성 기능에 실제 적용 완료.

**새로 추가된 것**
| Task | 왜 필요한가 |
|---|---|
| 아키텍처 다이어그램(mermaid) README 반영 | `docs/db-erd.md`는 DB 테이블 관계도뿐 — 화면→서버→DB "데이터 흐름"을 보여주는 다이어그램이 없음. PPT용으로 만든 Flow A(규칙→AI 시나리오 생성)·Flow B(AI 손님 대화) 트레이스를 mermaid로 옮겨 README에 추가 |
| Vitest 설정 + TDD 기능 1개 + 단위/통합 테스트 | 테스트가 하나도 없음. CLAUDE.md에 예고돼 있던 "코어 로직 생기면 Vitest 도입" 시점 |
| 테스트코드 생성 Skill 제작 | `.claude/skills/`에 신규 — 반복적으로 테스트를 짜야 할 때 재사용 |
| 나만의 Agent 워크플로우 문서화 | task-planner(계획) → 구현 → feature-verifier(검증) 흐름을 문서로 정리 |
| **기능 강화 ①** 루브릭 재사용성 (유사 매장 간 템플릿 공유·캐싱) | "핵심 기능 보완 + 사용성 강화 기능 1~2개" 요구사항 충족용, 7절 멘토링 피드백과도 일치 |
| **기능 강화 ②** 평가 결과 교차검증 (타 모델로 재검증) | 위와 동일 목적, 6절 멘토링 피드백에서 이미 3주차 Task로 있던 것을 "기능 강화" 대상으로 지정 |
| 시나리오 배치 생성 트랜잭션으로 묶기 | `stores.js`의 `POST /:linkKey/rules`가 `Promise.all`로 시나리오+루브릭 여러 개를 만드는데, 중간 실패 시 부분 데이터가 남을 수 있음(원자성 없음) |
| AI 응답 JSON 파싱 방어 | `evaluator.js`/`rubric.js`/`scenarioProposer.js`가 `JSON.parse(response.text)`를 그대로 믿음. `responseSchema` 강제해도 100% 보장 아님 — 오늘 발견한 "[필수]" 접두어 버그가 그 증거 |
| AI 호출 재시도 로직 | Gemini/OpenAI 호출이 한 번이라도 실패하면(타임아웃 등) 바로 실패 처리. 짧은 재시도(1~2회)로 일시적 실패에 대응 |
| eval 셋을 시나리오 제안·평가에도 확장 | 지금 `server/eval/rubric-eval-set.json`은 루브릭 생성만 커버 — 프롬프트 변경 시 회귀 확인 범위를 넓힘 |
| AI 호출 성공/실패·소요시간 로깅 | 지금은 `console.error`뿐이라 실패 패턴을 사후에 파악할 방법이 없음 |

**기존 3주차 계획 중 유지되는 것** — 화면 라우팅 골격(사장님/알바 경로 분리), 평가 에이전트 캘리브레이션, UI 디테일(로딩·에러·반응형·접근성), Railway/Supabase/Vercel 배포.

**진행 방식**: 미션 요구사항대로 "기능 강화 ①·②"는 AI와 함께 설계(task-planner 활용) → 작업을 작게 나눠 상위 조직 리포(`connect-AIAgentChallenge-26-1/hub`)에 이슈로 등록 → 개발 순서로 진행한다. 2주차 때 만든 트래킹 이슈(#787) 패턴을 그대로 따라, 3주차 전체를 담는 부모 이슈 아래 세부 이슈들을 자식으로 건다. 새 기능 구현을 시작할 땐 Plan Mode로 먼저 계획을 세운 뒤 단계적으로 진행한다(미션의 "Agent 활용" 요구사항).

**3주차 완료 기준**: 사장님/알바 경로가 라우팅으로 분리돼 있고, 루브릭 재사용·교차검증 기능이 실제로 동작하며, README의 다이어그램으로 전체 구조를 설명할 수 있고, 테스트(Vitest)가 최소 1개 기능을 커버한다.
