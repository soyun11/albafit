# ai-usage-and-cost-review.md — AI 호출 구조 정리 + 비용 효율성 검토 + LangChain/LangGraph 도입 검토

> `docs/staff-report-and-rubric-fix.md`와 같은 방식으로 기록한다. 처음 계획(plan.md 5절)엔 "손님 에이전트 / 평가 에이전트" 2개만 있었는데, 실제로는 4개까지 늘어나서 한 번 정리했다. 코드 변경은 없고 현재 상태 점검 + 내일 이후 방향 검토 문서다.

## 배경

plan.md와 CLAUDE.md에는 원래 "목적이 다른 두 개의 LLM 에이전트(손님/평가)가 상태를 주고받는 루프"라고 되어 있는데, 오늘 하루 개발하면서 실제로는 AI 호출 지점이 4곳으로 늘었다. 늘어난 만큼 API 비용도 늘어나는 구조라, 지금 구조가 효율적인지 점검하고 개선 방향과 LangChain/LangGraph 도입 여부를 검토한다.

## 2. 이벤트 하나당 실제 LLM 호출 횟수

기능 하나를 한 번 쓸 때 뒤에서 몇 번의 LLM 호출이 도는지 세어보면:

- **규칙 제출/재설정 1회** = Gemini **3회** — `stores.js`의 `Promise.all(scenarioDefs.map(...generateRubric...))`(`stores.js:209`)가 업종별 시나리오 수(보통 3개)만큼 병렬로 `generateRubric`을 부른다. 병렬이라 **응답 시간**은 줄지만 **API 비용**은 그대로 3배다.
- **매뉴얼 자동 분리 사용 시** = 위에 +1회(`splitManualRules`, `stores.js:113`).
- **훈련 세션 1회(3턴 고정, `sessions.js:11`의 `MAX_TURNS`)** = Gemini(평가) **3회** + OpenAI(손님) **2회** = 총 **5회**. 마지막 3턴째는 세션이 끝나서 다음 손님 대사를 안 만들기 때문에 손님 쪽은 2번만 돈다(`sessions.js:108-133`).
- **"기준 재설정"을 누를 때마다** 첫 번째 항목(Gemini 3회)이 그대로 다시 돈다 — 규칙 문구를 한 글자만 고쳐도 시나리오 3개 전부 처음부터 재생성.

정리하면 사장님 한 명이 온보딩(규칙 제출 1회) + 알바 훈련 3종 시나리오를 한 바퀴 돌리는 것만으로 **Gemini 12회(루브릭 3 + 평가 9) + OpenAI 6회** 정도가 나간다. 알바가 여러 명이면 평가·손님 쪽 호출은 인원수만큼 선형으로 늘어난다.

## 3. 지금 구조에서 비효율적인 지점

- **규칙 원문 중복 전송**: `generateRubric`이 시나리오 3개에 대해 각각 별도로 호출되는데, 매 호출마다 같은 `rawRulesText` 전체를 프롬프트에 다시 넣는다(`rubric.js:48`). 시나리오 3개 몫의 프롬프트 오버헤드(같은 규칙 원문 3벌)가 매번 청구된다.
- **재시도/에러 처리가 없다**: `gemini.js`/`openai.js`는 클라이언트를 그냥 export만 하고, 호출부(`rubric.js`/`evaluator.js`/`manualRules.js`/`customerAgent.js`) 각자 별도 처리 없이 실패하면 그대로 위로 던져서 라우트가 500을 낸다. 일시적 네트워크 오류에도 사용자가 처음부터 다시 눌러야 하고, 그때마다 이미 성공했던 호출까지 다시 도는 경우가 생길 수 있다.
- **재설정 시 변경 여부를 안 본다**: 규칙 내용이 실제로 안 바뀌었어도(예: 저장 버튼을 실수로 두 번 누름) 루브릭 3개를 처음부터 다시 생성한다 — diff 체크가 없다.
- **로깅이 없다**: 몇 번 호출됐는지, 토큰을 얼마나 썼는지 남기는 곳이 없어서 지금 이 문서의 "12회+6회" 같은 숫자도 코드를 직접 세어본 것이지 실제 운영 데이터가 아니다. 비용을 정말 관리하려면 이게 먼저 필요하다.

## 4. 개선 방향 (우선순위)

1. **호출 횟수/토큰 로깅 먼저** — 위 3가지 개선이 실제로 얼마나 절감되는지 알려면 지금 얼마나 쓰는지부터 재야 한다. `gemini.js`/`openai.js`에 호출 래퍼를 하나 두고 모델·토큰 수·성공여부를 로그로 남기는 게 제일 먼저 할 일.
2. **루브릭 3콜 → 1콜 배치화 검토** — 시나리오 3개를 한 프롬프트에 다 넣고 `{scenarios: [{type, criteria}, ...]}` 하나로 받으면 호출 수는 3→1, 규칙 원문 중복 전송도 없어진다. 다만 트레이드오프가 있다: 응답 JSON이 커지고 스키마가 복잡해지며, 한 시나리오만 이상해도 재시도하려면 3개를 통째로 다시 돌려야 한다(지금은 시나리오 단위로 개별 재시도가 가능). 사장님이 온보딩 중 눈으로 대기하는 시간이라 지연시간도 같이 고려해야 함 — 무조건 이득은 아니다.
3. **재시도 래퍼 추가** — 지수 백오프로 1~2회 재시도하는 공통 함수 하나 만들어서 4개 lib 파일이 같이 쓰게.
4. **재설정 시 규칙 원문 diff 체크** — 새로 제출된 `rawText`가 직전 저장분과 완전히 같으면 루브릭 재생성을 스킵.
5. **모델 티어링 재점검** — 매뉴얼 자동 분리(4번)는 "텍스트를 카드로 쪼개기"라 평가(2번)나 루브릭 생성(3번)보다 판단 난이도가 낮다. 지금은 다 같은 Gemini 모델을 쓰는데, 더 가벼운 하위 모델로 내려도 품질 차이가 없는지 확인해볼 가치가 있다.

우선순위는 1번(로깅) 없이 2~5번을 먼저 하면 "느낌상 개선"이지 실제 절감량을 모른다 — 그래서 로깅이 항상 맨 앞이다.

## 5. LangChain/LangGraph 도입 검토

### 지금 구조가 프레임워크를 필요로 하는가
4개 호출 지점 전부 **"프롬프트 하나 → 응답 하나"** 형태의 단일 요청-응답이다. 여러 LLM 호출을 체이닝하거나(한 호출 결과로 다음 호출 프롬프트를 동적으로 구성), 도구 호출을 반복하거나, 실패 시 다른 경로로 분기하는 멀티스텝 로직은 아직 없다. LangChain의 핵심 가치(프롬프트 템플릿 관리, 출력 파서, 여러 모델·툴을 체인으로 엮기)나 LangGraph의 핵심 가치(상태를 가진 멀티노드 그래프, 조건 분기, 사이클)가 풀어줄 문제가 지금은 없다는 뜻이다. 지금 필요한 건 "재시도·로깅을 공통화하는 것"이지 "체인을 짜는 것"이 아니다 — 3절의 문제들은 얇은 공통 래퍼 함수 하나로 해결되는 수준이라 프레임워크 도입은 오히려 의존성과 학습 비용만 늘린다.

### 중요한 전제: 프레임워크는 비용을 줄여주지 않는다
LangChain/LangGraph를 쓴다고 API 비용이 내려가지 않는다. 오히려 LangGraph의 agent executor 패턴(스스로 판단해서 도구를 반복 호출하는 루프)은 잘못 설계하면 **호출 횟수가 늘어날 위험**이 있다. 비용은 "호출을 몇 번 하느냐/프롬프트에 뭘 넣느냐"라는 설계 문제고, 프레임워크는 그 설계를 표현하는 도구일 뿐이다. 4절의 개선안(배치화·캐싱·재시도)은 프레임워크 유무와 무관하게 지금 코드에 바로 적용 가능하다.

### 그래도 도입을 고려해볼 지점 — 내일의 시나리오 제안
`docs/scenario-generation-redesign.md`에서 설계한 "규칙 원문 → 시나리오 후보 생성 → 사장님 승인 → (반려 시) 재생성" 흐름은 지금 4개 호출과 다르게 **여러 단계 + 사장님 승인이라는 명시적 분기**가 있는 멀티스텝 파이프라인이다. CLAUDE.md의 "AI는 생성, 사장님은 승인" 원칙 자체가 생성 노드 → 승인 게이트 → (반려 시) 재생성 노드로 그래프처럼 표현될 수 있는 구조라, 이 파이프라인이 실제로 여러 단계로 늘어나면(예: 후보 생성 → 자체 검증 → 재생성까지 자동화) 그때는 LangGraph의 `StateGraph`가 지금 손코딩한 상태 관리보다 나을 수 있다.
다만 지금 계획(`docs/scenario-generation-redesign.md`)의 범위는 "생성 1번 호출 + 사장님이 수동 승인/반려" 정도라 이것도 아직은 단일 호출 수준이다 — 실제로 도입 판단은 그 기능을 만들면서 "여러 LLM 호출이 서로의 출력에 의존하며 3단계 이상 이어지는지"를 보고 그때 다시 결정하는 게 맞다.

### 결론
- 지금(4개 호출 지점)은 프레임워크 도입 실익이 없다 — 각 lib 파일을 독립 함수로 유지하는 지금 방식(CLAUDE.md가 원래도 "SDK 직접 호출" 기조)이 4주 챌린지 규모엔 맞다.
- 비용 문제는 프레임워크가 아니라 4절의 개선안(로깅→배치화/재시도/diff체크)으로 접근한다.
- LangGraph는 "도입할지 말지"를 지금 결정하지 말고, 내일 시나리오 제안 기능을 만들다가 멀티스텝 의존 관계가 실제로 생기면 그 시점에 다시 검토한다.

## 검증
- 코드 변경 없는 조사/설계 문서라 별도 실행 검증은 없음 — 2절의 호출 횟수는 `stores.js`/`sessions.js`/`guest.js`를 직접 읽고 각 호출부(`Promise.all`, `MAX_TURNS` 루프)를 세어 확인함.
