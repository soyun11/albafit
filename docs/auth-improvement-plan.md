# auth-improvement-plan.md — 로그인 시스템 개선 1단계 (이메일 인증 + 리프레시 토큰)

> 2026-07-15에 만든 로그인 시스템(`server/src/routes/auth.js`, `docs/db-schema.md`의 `users` 테이블)을 개선하는 실행 계획. `docs/db-migration-plan.md`와 같은 방식으로 기록을 남긴다.

## 원래 어떻게 만들었는지 (2026-07-15 최초 구현)

로그인 기능을 처음 만들 때, "오늘 6시간 안에 끝내야 한다"는 시간 제약 때문에 의도적으로 최소 범위로 잡았다:
- `server/src/routes/auth.js`에 `POST /signup`(사장님 전용 회원가입), `POST /login`, `GET /me`, `PATCH /password` 4개 라우트만 만들었다.
- 인증은 bcrypt(비밀번호 해싱) + JWT(로그인 상태 유지용 토큰) 조합. 토큰은 발급 후 7일 동안 유효하고, 그 안에 만료 처리·재발급 로직은 없다.
- 회원가입 시 이메일이 실제로 존재하는지 확인하는 절차가 없다 — 아무 문자열이나 이메일 형식만 맞으면 가입된다.
- 로그인 실패를 여러 번 반복해도 막는 장치(rate limiting)가 없다.

이 네 가지 중 뒤의 두 개(이메일 미확인, 토큰 재발급 없음)를 오늘 개선한다. 세 번째(rate limiting)는 사용자가 "지금은 안 해도 된다"고 확인해서 이번 범위에서 뺀다.

## 무엇을 바꾸는지 (요약)

1. **이메일 인증** — 사장님이 회원가입할 때 입력한 이메일이 실제로 본인 것인지 메일로 확인한다.
2. **리프레시 토큰** — 로그인 상태를 "짧게 유효한 카드 + 그 카드를 재발급받는 긴 카드" 2단계로 나눠서, 토큰이 새어나가도 피해를 줄이고 서버가 강제로 로그아웃시킬 수 있게 한다.

## 선택 근거 (비교안)

### 이메일 발송 서비스

| 옵션 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| **Resend (채택)** | 개발자용 API가 간단(코드 몇 줄), 하루 100통 무료, Node 공식 SDK 있음 | 계정 새로 만들고 API 키 발급해야 함 | **채택** |
| Gmail(SMTP) 직접 연동 | 가입 없이 기존 Gmail 계정 재사용 가능 | 구글 "앱 비밀번호" 발급 등 설정이 더 번거롭고, 대량 발송 시 스팸 처리 위험 | 기각 |
| AWS SES | 대량 발송에 강함, 저렴 | AWS 계정·리전·발신 도메인 인증 등 설정이 4주 챌린지엔 과함 | 기각 |

**결론**: 지금 필요한 건 "회원가입 시 확인 메일 한 통"이 전부라 설정이 제일 간단한 Resend를 선택.

### 이메일 인증 대상

| 옵션 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| **사장님 회원가입만 (채택)** | 셀프 가입(=본인이 직접 이메일을 입력)하는 쪽만 검증하면 충분 | 알바 이메일이 사장님의 오타일 가능성은 못 잡음 | **채택** |
| 사장님+알바 둘 다 | 모든 계정의 이메일이 확실해짐 | 알바는 사장님이 계정을 만들어주는 방식이라, 알바 본인이 첫 로그인하기도 전에 인증 메일부터 받는 흐름이 어색함 | 기각 |

**결론**: 이메일을 "본인이 직접 입력"하는 경우에만 검증이 의미가 있다. 알바 계정은 사장님이 만들어주므로, 알바가 다른 사람 이메일로 잘못 만들어졌는지는 이메일 인증이 아니라 다른 방법(예: 계정 목록에서 사장님이 직접 확인)으로 해결할 문제.

### 리프레시 토큰 구현 수준

| 옵션 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| **DB 저장 + 재사용 감지(로테이션) (채택)** | 토스·카카오 등 실제 서비스가 쓰는 표준 방식. 서버가 특정 사용자를 강제 로그아웃시킬 수 있고, 토큰이 복사돼도 재사용 시점에 감지 가능 | 테이블 하나(`RefreshToken`) 추가, 로그인·재발급·로그아웃 로직이 조금 더 복잡해짐 | **채택** |
| 단순히 긴 JWT 하나 더 발급(DB 저장 안 함) | 구현이 훨씬 간단 | 강제 로그아웃 불가능, 토큰이 새어나가도 감지·차단 방법이 없음 — 지금 방식(액세스 토큰만 7일)의 문제를 사실상 그대로 갖고 있음 | 기각 |

**결론**: 지금 방식의 진짜 문제(강제 무효화 불가능)를 고치려면 DB 저장이 필수. 여러 기기 로그인 목록 관리 같은 확장 기능은 이번 범위에 넣지 않는다.

## 현재 상태 (개선 전 기준)

- `server/prisma/schema.prisma`에 `User` 모델은 있지만 `emailVerifiedAt`, 리프레시 토큰 관련 테이블은 없다.
- `server/src/lib/auth.js`의 `signToken`이 액세스 토큰 하나만 만들고, 만료는 7일(`expiresIn: '7d'`) 고정.
- `server/src/routes/auth.js`에 로그아웃 라우트 자체가 없다 — 지금 "로그아웃"은 프론트(`src/lib/api.js`의 `clearToken`)가 브라우저에 저장된 토큰을 지우는 것뿐이고, 서버는 그 토큰이 여전히 유효하다고 생각한다.
- 이메일 발송 관련 코드·의존성 없음.

## 실행 완료 + 발견한 버그 3개 (2026-07-15)

계획대로 구현 후 실제 도메인(`albafit.kr`, 가비아 구매 + Resend 도메인 인증 완료)까지 연결해서 curl과 브라우저로 검증하는 과정에서 버그 3개를 발견해 그 자리에서 고쳤다.

### 버그 1 — RESEND_API_KEY 없으면 서버 전체가 죽음
`server/src/lib/email.js`가 모듈이 로드되는 시점(`import` 시점)에 `new Resend(process.env.RESEND_API_KEY)`를 바로 실행했는데, Resend SDK는 키가 없으면 생성자에서 즉시 예외를 던진다. 키를 아직 안 넣은 로컬 환경(`RESEND_API_KEY=""`)에서 서버 자체가 부팅도 못 하고 죽는 문제였다. **수정**: Resend 클라이언트를 모듈 로드 시점이 아니라 `sendVerificationEmail()` 호출 시점에 필요할 때만 생성하도록 `getClient()` 함수로 감쌌고, 키가 없으면 메일 발송만 건너뛰고 서버는 정상 동작하게 했다.

### 버그 2 — Resend 발송 실패가 조용히 성공으로 처리됨
도메인 인증 전, 테스트로 `567654@naver.com`(Resend 계정 소유자의 이메일이 아닌 주소)에 인증 메일을 보냈는데 도착하지 않았다. 원인을 추적해보니 **Resend SDK의 `emails.send()`는 실패해도 예외를 던지지 않고 `{ data: null, error: {...} }` 형태로 결과만 반환**한다 — `email.js` 코드가 이 반환값을 확인하지 않고 그냥 무시했기 때문에, 도메인 미인증으로 발송이 거부(403)돼도 회원가입 API는 200번대로 성공 응답을 줬다. **수정**: `sendVerificationEmail()`이 `error` 필드를 직접 확인해서 있으면 예외를 던지도록 고쳤다. 이후 `albafit.kr` 도메인을 Resend에 인증하고(가비아 DNS에 DKIM/SPF/DMARC 레코드 추가) 재검증해서 `567654@naver.com`으로 실제 메일 수신까지 확인했다.

### 버그 3 — React StrictMode가 인증 링크를 두 번 호출해 성공을 실패로 보여줌
`VerifyEmail.jsx`가 실제로는 인증에 성공했는데도 화면엔 "인증에 실패했어요"로 떴다. 원인은 React 18 `StrictMode`(개발 모드에서 부수효과 버그를 잡으려고 `useEffect`를 의도적으로 두 번 실행시킴) — 인증 토큰은 한 번 쓰면 서버에서 바로 삭제되는 1회용인데, 가드 없이 두 번 호출되면서 첫 번째 호출은 성공(토큰 삭제)하고 곧바로 이어진 두 번째 호출은 "이미 없는 토큰"이라 실패했고, 마지막에 반영된 상태가 실패였던 것. `GET /api/auth/me`로 실제 DB의 `emailVerifiedAt`을 확인해서 인증 자체는 성공했음을 먼저 확인했다. **수정**: `useRef`로 "이미 요청했는지" 가드를 추가해서, StrictMode가 effect를 두 번 실행시켜도 실제 API 호출은 한 번만 나가게 했다.

## 완료 기준

- [x] 사장님 회원가입 시 실제로 메일이 오고, 링크를 눌러야 `emailVerifiedAt`이 채워진다. — `albafit.kr` 도메인으로 `567654@naver.com`에 실제 발송·인증 완료까지 확인.
- [x] 액세스 토큰이 1시간 뒤 만료돼도 화면이 끊기지 않고 자동으로 새 토큰을 받아온다. — curl로 401 → refresh → 재시도 흐름 확인.
- [x] 이미 사용된(로테이션된) 리프레시 토큰을 다시 쓰면 그 사용자의 모든 리프레시 토큰이 무효화된다. — curl로 재사용 시 두 토큰 다 401 되는 것 확인.
- [x] 로그아웃하면 서버에도 반영돼(리프레시 토큰 revoke), 그 토큰으로는 더 이상 재발급이 안 된다. — curl로 확인.
