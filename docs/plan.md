# plan.md — 매장 맞춤 알바 훈련 서비스

## 한 줄 정의

**사장님이 매장 응대 기준을 한 번 입력해두면, 새 알바가 올 때마다 AI 손님과 실전처럼 대화 연습을 하고 그 기준에 맞춰 교정 피드백을 받는 웹 서비스.** 핵심은 "이 매장의 기준을 사장님이 정의하고, 사람이 바뀌어도 재사용한다"는 구조에 있다.

---

## 1. 문제 정의

### 1-1. 한 문장 (해결책 없이 문제만)

> 소상공인 매장은 알바 교체가 잦고 메뉴·규칙도 수시로 바뀌는데, 사장님은 새 알바마다 응대 기준을 반복 설명할 시간과 여력이 없다. 그 결과 누가 언제 일하느냐에 따라 응대 품질이 들쭉날쭉해진다.

### 1-2. 왜 "편차" 프레임인가

"신입 첫날 온보딩"에만 초점을 두면 일회성 문제로 보인다. 하지만 알바는 회전하는 인력이라, 반복되는 것은 알바의 학습이 아니라 **사장님의 반복 설명 부담**이다. 그래서 문제의 축을 "초기 실수"가 아니라 "누가 일하든 응대 품질이 흔들리는 편차"로 둔다. 다시 찾는 주체는 알바가 아니라 사장님이다.

### 1-3. 문제의 실재성 (통계 근거)

음식·숙박업은 세 조건이 겹친다. (출처: 고용노동부 사업체노동력조사 2024.6, 산업연구원 인력통계, e-나라지표)

- **고회전** — 2024년 6월 전 산업 월평균 이직률 4.9%(월 기준), 숙박·음식점업은 종사자가 지속적으로 빠진다(한 달 -3만 명, -2.5%; 대전 7.9% 등 지역별 상위권). → 반복 설명이 실제로 반복된다.
- **인력 부족** — 숙박·음식점업 인력부족률 전 산업 최상위권. → 신입을 빨리 전력화해야 한다.
- **저교육 여력** — 월평균 임금 약 234만 원으로 전 산업 최하위권, 임시·일용직 비중 높음. → 교육 시스템을 둘 여력이 없어 교육이 사장님 몫이 된다.

세 조건이 겹쳐 **교육 공백이 구조적으로 생기는 시장**이다. (수치는 월·지역별 편차가 커 "전 산업 대비 높고 지속적"이라는 방향으로 서술한다.)

### 1-4. 경쟁·유사 서비스

AI 응대 훈련 시장은 이미 검증됐지만, 전부 대기업을 향한다.

| 서비스 | 대상 | 우리와의 차이 |
|---|---|---|
| 딥브레인AI 'AI 롤플레이' | 보험설계사·영업팀(B2B) | 구조는 유사하나 대기업 영업 조직용, 도입에 시간·비용 큼 |
| Jenova 등 해외 롤플레이 | 기업 교육(L&D) | 글로벌 기업 대상, 개인 사장님은 타깃 아님 |

**우리의 빈틈**: 반복 교육 부담이 가장 큰 개인 소상공인을 아무도 제대로 보지 않는다. 무기는 AI 성능이 아니라 **저마찰 진입(로그인 없음, 5분 규칙 입력, 매장 링크 전달) + 이 매장 규칙에 그라운딩된 채점**이다.

> "AI 응대 훈련은 이미 검증됐지만 전부 대기업용이다. 우리는 그걸 개인 사장님이 오늘 당장 쓸 수 있게 만든 첫 서비스다."

## 2. 사용자 시나리오

- 카페 사장님이 신입 알바 지우가 출근하기 전, 매장 규칙과 자주 발생하는 응대 상황(음료 지연·품절·규칙 위반 손님)을 서비스에 미리 입력해둔다.
- 첫 출근 날, 지우는 훈련 시나리오를 골라 AI 손님과 대화를 연습한다.
- 지우가 "죄송합니다, 확인해보겠습니다"라고 답하자, AI는 "사과는 좋지만 예상 대기시간 안내가 빠졌다"고 피드백하며 개선 문장을 제안한다.
- 지우는 다시 연습해 만족스러운 수준에 도달한 뒤 실제 근무에 투입된다.
- 사장님은 반복 설명할 필요가 줄었다고 느끼고, 다음 알바에게도 같은 규칙을 재사용하면 된다고 생각한다.

## 3. 사용자 흐름

## 4. 핵심 기능 2개

### A — AI 손님과의 상황극 대화
시나리오 기반으로 손님 에이전트가 손님을 연기하며, 매장 규칙·페르소나·시나리오 상태(주문 상태·손님 기분·경과 턴)를 반영한다. 알바 답변에 따라 다음 반응이 분기된다.

### B — AI 피드백 및 평가
평가 에이전트가 알바 답변이 매장 규칙(루브릭)을 충족했는지 항목별로 판단하고, 미충족 시 개선 문장을 제안한다.

### 왜 이 2개인가

- **필수성**: A·B가 없으면 "훈련"이 성립하지 않는다. 규칙 입력·시나리오 선택은 이 둘을 작동시키는 설정일 뿐이고, 사용자가 가치를 느끼는 순간은 "대화하고(A) → 교정받는(B)" 지점뿐이다.
- **적합성**: 문제는 "사장님이 반복 설명할 여력이 없다"였다. A가 사장님의 구두 설명을 대체하고, B가 "그냥 연습"을 "매장 기준에 맞게 교정된 연습"으로 만들어 재설명 부담을 줄인다. A만 있으면 부담이 주는지 알 수 없고, B만 있으면 평가할 대화가 없다. **둘은 서로를 완성시키는 한 쌍이다.**

### 뺀 것들

- **매장 규칙 입력**: 선행 설정. 단, 입력된 규칙이 **루브릭으로 변환되어 B의 채점 근거가 된다**는 점에서 품질이 가장 중요한 화면이다.
- **재연습 루프**: B의 파생 동작이지 독립 기능이 아니다.
- **결과 리포트**: 없어도 훈련은 완결된다 → 코어 아님. 사장님 재방문을 유도하는 확장 1순위.
- **로그인**: 저마찰 진입을 위해 의도적으로 제외(시나리오는 매장 링크 단위로 누적).

## 5. 구현 아키텍처

### 5-1. 두 개의 에이전트로 분리

코어는 목적이 다른 두 개의 에이전트가 상태(대화 히스토리·시나리오 상태·루브릭)를 주고받으며 도는 루프다.

| 에이전트 | 하는 일 | 모델 | 할루시네이션 위험 |
|---|---|---|---|
| **손님 에이전트** | 페르소나·상태 유지하며 애드리브, 답변에 따라 반응 분기 | Claude Haiku 4.5 (빠름·저렴, 호출 잦음) | 낮음 (애드리브가 자산) |
| **평가 에이전트** | 루브릭 항목별 채점, 통과/재시도 분기 결정 | Claude Sonnet 5 (판단 신중) | **높음 — 방어 필수** |

- **두 에이전트는 절대 한 호출로 합치지 않는다** — 시스템 프롬프트도, 요구 품질도, 쓰는 모델도 다르다.
- 상태 전달(대화 히스토리·시나리오 상태·루브릭)은 애플리케이션 코드가 관리하고, 데이터 접근은 MCP 서버(5-6)를 통해 한다.
- v1은 순수 API 호출로 먼저 안정성을 확보한 뒤 MCP로 전환한다. 진짜 어려운 건 루브릭 품질·평가 신뢰성·입력 UX다.

### 5-2. 루브릭 = 할루시네이션 방어막

루브릭은 사장님 규칙을 AI가 체크 가능한 채점표로 쪼갠 것이다. "지연 시 예상 대기시간을 안내하라" →

```
① 사과 표현이 있는가 (must)
② 예상 대기시간을 안내했는가 (must)
③ 금지 표현을 쓰지 않았는가 (must)
```

- **핵심 원리**: 평가자에게 "잘했어?"라고 열린 질문을 하면 헛소리를 하지만, "①②③ 있는지 체크만 해"로 좁히면 일이 **창작에서 확인으로 바뀌어** 할루시네이션이 급감한다. 이 변환의 품질이 제품 품질을 결정한다.
- **추가 방어 ①** — 판단 근거를 규칙 인용으로 대게 한다("②번 미충족: 'ETA 안내' 규칙").
- **추가 방어 ②** — 초기엔 사장님이 평가 결과 몇 개를 검토·교정해 캘리브레이션한다.
- **위험 위치**: 할루시네이션 위험은 전부 평가 에이전트에 몰려 있다(손님이 사실을 지어내도 훈련 소재라 무해).

### 5-3. 입력 흐름: AI 초안 + 사장님 승인

```
업종 선택 → AI가 업종 템플릿(질문 세트) 제시 → 사장님이 자연어로 답 채움
        → AI가 루브릭·시나리오 초안 생성 → 사장님 승인/수정 → 확정
```

- **원칙: AI는 생성, 사장님은 승인** — AI가 규칙을 통째로 지어내면 "이 매장 기준"이 아니라 "AI가 상상한 일반 기준"이 되어 차별점이 사라진다.
- **AI가 아는 범위**: "카페엔 이런 상황이 있다"는 업종 상식까지만. "스타벅스는 환불이 이렇다"는 브랜드 정책은 몰라야 한다(지어내면 할루시네이션).
- **브랜드별 차이 해결**: AI가 질문을 깔고 사장님이 답을 채우는 업종 템플릿으로 푼다.

### 5-4. 모달리티: 텍스트 턴제 채팅

- **왜 텍스트인가**: 신입이 첫날 못 하는 건 "톤"보다 "무슨 내용을 말하나"다. 내용을 먼저 잡는 게 학습 순서상 맞다.
- **왜 음성 아닌가**: 음성은 STT가 새 할루시네이션 소스가 되어 평가 신뢰성을 흔든다 → v1에서 제외.
- **형식**: 턴제 실시간 채팅(손님 한 마디 → 알바 답변 → 즉시 평가 → 다음 턴). 한 마디마다 교정된다.

### 5-5. 기술 스택 & 데이터

- 프론트 React / 백엔드 Express / DB PostgreSQL(매장→규칙→루브릭→시나리오→세션의 FK 관계, 구조가 바뀌는 값은 JSONB)
- **배포**: 백엔드·DB는 Railway, 프론트는 Vercel. 1주차에 빈 껍데기로 미리 배포해 파이프라인을 검증하고, 4주차에 완성본을 올린다.
- AI 로직은 순수 API 호출로 먼저 구현. 평가 에이전트 출력은 **반드시 JSON**(`{충족여부, 빠진기준[], 피드백, 개선문장}`)으로 강제.
- 저장의 루트는 매장 링크(`link_key`). 알바는 계정 없이 자유 라벨(`staff_label`)만 남긴다. 상세 스키마는 [db-schema.md](/hub/docs/db-schema.md) 참고.

### 5-6. MCP 서버 (에이전트–데이터 연결)

두 에이전트가 DB를 직접 쿼리하지 않고 **MCP 서버가 노출하는 tool을 통해** 데이터에 접근한다. 데이터 접근 로직을 한 곳에 모아, 에이전트는 "무엇을 할지"만 결정하고 "어떻게 가져올지"는 MCP가 담당한다.

- `get_store_rules` / `get_rubric` — 손님·평가 에이전트가 매장 규칙·루브릭을 읽어올 때
- `save_session_turn` — 평가 에이전트가 턴 결과를 기록할 때
- `get_session_report` — 사장님 리포트 집계

v1은 순수 API 호출로 먼저 동작을 확보하고, 4주차에 이 데이터 접근을 MCP tool call로 전환한다(동작 회귀는 1주차의 eval 셋을 재사용해 확인).

## 8. 남은 검증 과제

1. AI 평가 신뢰성 — 체크리스트 기반 정량 평가로 설계(5-2).
2. 문제 실재성 — 소상공인/알바 인터뷰로 "돈 낼 만한가" 검증.
3. 비즈니스 모델 — 지불 주체·가격 가설(예: 월 3만 원).
4. 핵심 가치 — "구두 설명 대비 실제로 더 나은가" 인터뷰.
5. 타깃 — "회전은 있으나 최소한의 온보딩 여유가 있는" 매장으로 좁힘.

## 9. 성공 지표

기능이 도는가가 아니라 **사장님의 반복 설명이 줄었는가**를 본다.

**North Star: 매장당 한 달 재훈련 세션 수** — 같은 매장 링크가 새 알바가 올 때마다 다시 쓰이는 횟수. 문제의 축이 "반복되는 편차"이고 다시 찾는 주체가 사장님이므로, 이 숫자가 문제 해결의 가장 직접적 증거다.

선행 지표: 두 번째 이상 세션 생성 비율(재방문), 규칙 입력→루브릭 승인 완료율(저마찰), 세션 완료율·재시도(적정 난이도), 사장님 캘리브레이션 동의율(평가 신뢰), 유료 전환 의향(인터뷰 기반).
