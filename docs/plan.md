# plan.md — 매장 맞춤 알바 훈련 서비스

## 한 줄 정의

**매장 맞춤 알바 훈련 서비스.** 사장님이 매장 응대 기준을 한 번 입력해두면, 새 알바가 올 때마다 AI 손님과 실전처럼 대화 연습을 하고, 그 기준에 맞춰 교정 피드백을 받는 웹 서비스다.

롤플레잉은 이 서비스를 구현하는 수단이지 정체성이 아니다. 핵심은 "이 매장의 기준을 사장님이 정의하고, 사람이 바뀌어도 재사용한다"는 구조에 있다.

---

## 1. 문제 정의

### 1-1. 한 문장 (해결책 없이 문제만)

> 소상공인 매장은 알바 교체가 잦고 메뉴·규칙도 수시로 바뀌는데, 사장님은 새 알바마다 응대 기준을 반복 설명할 시간과 여력이 없다. 그 결과 누가 언제 일하느냐에 따라 응대 품질이 들쭉날쭉해진다.

(원안: "소상공인 사장님은 신입 알바가 손님 응대 상황에서 당황하거나 실수해도, 매번 반복해서 직접 설명해줄 시간과 여력이 없다." — 위 문장은 원안의 "매번 반복"이 왜 지속되는지를 명시해 일회성 프레임을 넘어선 버전이다.)

### 1-2. 왜 "편차" 프레임인가 (리프레임 근거)

처음 기획은 "신입 알바 첫날 온보딩"에 가치가 몰려 있어 일회성으로 읽혔다. 알바는 본질적으로 회전하는 인력이라 반복 사용이 생기지 않지만, **사장님의 문제(교체·규칙 변경마다 반복 설명)는 사라지지 않는다.** 따라서 문제의 축을 "초기 실수"에서 "누가 일하든 응대 품질이 흔들리는 편차"로 옮긴다. 재방문 엔진은 알바가 아니라 사장님 쪽에 있다.

### 1-3. 문제의 실재성 (통계 근거)

음식·숙박업은 다음 세 조건이 겹치는 업종이다. (출처: 고용노동부 사업체노동력조사, 산업연구원 인력통계, 통계청 KOSIS)

- **고회전**: 전 산업 월평균 이직률이 5% 안팎인데, 숙박·음식점업은 종사자가 지속적으로 빠지는 산업으로 나타난다(2024년 6월 기준 한 달 -3만 명, -2.5%). 시도별로도 이직률이 상위권(예: 2024.6 대전 7.9%).
- **인력 부족**: 2025년 10월 기준 숙박·음식점업 인력부족률 3.9%로 전 산업 최상위권. 어렵게 뽑은 신입을 빨리 전력화할 필요가 크다.
- **저교육 여력**: 숙박·음식점업 월평균 임금총액 약 234만 원으로 전 산업 최하위권, 임시·일용직 비중이 높다. 정식 교육 시스템을 갖추기 가장 어려운 업종이면서 회전은 가장 빠르다.

→ 즉 **고회전·인력부족·저임금의 삼중고 업종**이라 "알바가 바뀔 때마다 응대 품질이 흔들리는" 문제가 구조적으로 발생한다. (주의: 이직률은 월·지역별 편차가 커 단일 숫자로 못 박지 않고 "전 산업 대비 높고 지속적"이라는 방향으로 서술한다.)

### 1-4. 경쟁·유사 서비스 분석

AI 응대 훈련 시장은 이미 검증됐다. 문제는 **전부 대기업·엔터프라이즈를 향한다는 것**이다.

| 서비스 | 대상 | 특징 | 우리와의 차이 |
|---|---|---|---|
| 딥브레인AI 'AI 롤플레이' (2026) | 보험설계사·영업팀 (B2B) | AI 고객 실시간 응대, 종료 후 말하기 점수·개선점 자동 코칭 | 구조는 매우 유사하나 **대기업 영업 조직용**, 도입에 시간·비용이 큼 |
| Jenova 등 해외 AI 롤플레이 | 기업 교육(L&D) | 적응형 난이도, 일관된 채점, 인증까지 무제한 연습 | **글로벌 기업 대상**, 개인 사장님은 타깃 아님 |

**우리의 빈틈**: 반복 교육 부담이 가장 큰 곳은 교육 시스템을 갖출 수 없는 개인 소상공인인데, 아무도 이 세그먼트를 제대로 보지 않는다. 우리의 무기는 AI 성능이 아니라 **저마찰 진입(로그인 없음, 5분 규칙 입력, 매장 링크 전달)** + **이 매장 규칙에 그라운딩된 채점**이다.

> 한 문장: "AI 응대 훈련은 이미 검증됐지만 전부 대기업용이다. 우리는 그걸 개인 사장님이 오늘 당장 쓸 수 있게 만든 첫 서비스다."

**리스크(인지)**: 딥브레인AI가 소상공인 시장으로 내려오면 위협. 그래서 방어선은 모델 성능이 아니라 "매장 규칙 그라운딩 + 저마찰 UX"여야 한다. 또한 이직률이 극히 높은 매장은 훈련에 쓸 시간조차 없을 수 있어(훈련이 필요한 곳일수록 못 쓰는 역설), 초기 타깃은 "회전은 있지만 최소한의 온보딩 여유가 있는" 매장으로 좁힌다.

## 2. 사용자 시나리오

- 카페를 운영하는 사장님은 신입 알바 지우가 출근하기 전, 매장 규칙과 자주 발생하는 응대 상황(음료 지연, 품절, 규칙 위반 손님 등)을 서비스에 미리 입력해둔다.
- 첫 출근 날, 지우는 실제 업무를 시작하기 전 훈련 시나리오를 골라 AI 손님과 대화를 연습한다.
- 지우가 "죄송합니다, 확인해보겠습니다"라고 답하자, AI는 "사과는 좋지만 예상 대기시간 안내가 빠졌다"고 피드백하며 개선 문장을 제안한다.
- 지우는 피드백을 참고해 다시 답변을 연습하고, 만족스러운 수준에 도달한 뒤 실제 근무에 투입된다.
- 사장님은 지우가 첫 근무에서 비교적 당황하지 않고 응대하는 모습을 보며 반복 설명할 필요가 줄었다고 느낀다.
- 다음 알바를 뽑을 때도 같은 규칙으로 훈련시키면 되겠다고 생각한다. (규칙은 한 번 입력하면 계속 재사용되는 자산)

## 3. 사용자 흐름

세 구역으로 나뉜다: **사장님 설정 → 알바 훈련 → 결과 확인.** 로그인 없이 사장님은 바로 업종 선택으로 진입하고, 알바는 매장 링크로 진입한다.

핵심은 두 개의 되돌아가는 고리다:
- **사장님 승인 루프**: AI가 만든 루브릭·시나리오 초안을 사장님이 검토하고 수정 → "AI는 생성, 사장님은 승인" 원칙.
- **루브릭 평가 루프**: 알바 답변이 기준 미충족이면 개선 문장과 함께 재입력 → 제품의 핵심 교정 루프.

## 4. 핵심 기능 2개

### 기능 A — AI 손님과의 상황극 대화
시나리오 기반으로 AI가 손님을 연기하며, 사장님이 입력한 매장 규칙·페르소나·시나리오 상태(주문 상태, 손님 기분, 경과 턴)를 반영한다. 알바 답변에 따라 다음 반응이 분기된다.

### 기능 B — AI 피드백 및 평가
알바 답변이 매장 규칙(루브릭)을 충족했는지 항목별로 판단하고, 미충족 시 개선 문장을 제안한다.

### 왜 이 2개인가

**필수성** ("없으면 서비스가 안 돌아가나?"): A·B가 없으면 "훈련"이라는 개념 자체가 성립하지 않는다. 시나리오 선택·규칙 입력 화면은 이 둘을 작동시키기 위한 설정일 뿐이고, 사용자가 가치를 체감하는 순간은 오직 "대화하고(A) → 교정받는(B)" 지점이다.

**적합성** ("문제를 정확히 해결하나?"): 문제는 "사장님이 반복 설명할 시간·여력이 없다"였다. A(대화 연습)가 있어야 사장님의 구두 설명을 대체하고, B(평가·피드백)가 있어야 "그냥 연습"이 아니라 "매장 기준에 맞게 교정된 연습"이 되어 나중에 다시 고쳐줄 필요가 줄어든다. A만 있으면 AI와 대화만 하고 끝이라 부담이 주는지 알 수 없고, B만 있으면 평가할 대화가 없어 성립이 안 된다. **A와 B는 서로를 완성시키는 한 쌍이다.**

### 뺀 것들에 대한 근거

- **매장 규칙 입력**: A·B의 선행 설정 단계다. 단, 단순 입력 폼이 아니라 **입력된 규칙이 루브릭(채점 기준)으로 변환되어 B의 평가 근거가 된다**는 점에서 코어를 떠받치는 토대다. "기능"으로 분류하진 않되, 품질이 가장 중요한 화면으로 본다.
- **재연습 루프**: B(피드백)의 자연스러운 파생 동작이지 독립 기능이 아니다.
- **결과 리포트**: 없어도 A·B만으로 훈련은 완결된다 → 코어 아님. 다만 **사장님 재방문을 유도하는 확장 1순위.**
- **로그인**: 저마찰 진입을 위해 의도적으로 제외. (트레이드오프: 영속성이 약해지므로 시나리오는 매장 링크 단위로 누적되게 설계한다.)

## 5. 구현 아키텍처

### 5-1. 핵심 원칙: agent가 아니라 두 역할로 분리된 LLM 호출

자율적으로 계획·도구사용하는 agent는 v1에 과잉이다. 실제 필요한 것은 두 개의 분리된 LLM 호출이다.

| 역할 | 하는 일 | 요구 특성 | 모델 방향 | 할루시네이션 위험 |
|---|---|---|---|---|
| **AI 손님** | 페르소나 유지하며 애드리브 대화 | 창의성·속도 | 빠르고 저렴한 모델 | 낮음 (애드리브가 오히려 자산) |
| **AI 평가자** | 루브릭 항목별 채점, JSON 출력 | 지시 준수·구조화 | 신중한 중상급 모델 | **높음 — 방어 필수** |

두 역할을 절대 한 호출로 합치지 않는다. 시스템 프롬프트도, 품질 요구도, 쓸 모델도 다르다. (구체 모델명·가격은 착수 시점에 최신 스펙 확인. 역할이 분리돼 있어 손님 모델만 나중에 더 싼 것으로 교체하기도 쉽다.)

LangGraph 등 agent 프레임워크는 v1에서 쓰지 않는다. 순수 API 호출로 먼저 안정성을 확보하고, 여유가 있으면 리팩터링한다. 기술 복잡도가 낮은 건 좋은 신호다 — 진짜 어려운 건 루브릭 품질·평가 신뢰성·입력 UX이지 프레임워크가 아니다.

### 5-2. 루브릭 = 할루시네이션 방어막

루브릭은 사장님 규칙을 AI가 체크 가능한 채점표로 쪼갠 것이다. 예를 들어 "음료 지연 시 예상 대기시간을 꼭 안내하라"는 규칙은 이렇게 변환된다:

```
[음료 지연 시나리오 루브릭]
① 사과 표현이 있는가        (must)
② 예상 대기시간을 안내했는가  (must)
③ 금지 표현("안 돼요" 등)을 쓰지 않았는가  (must)
```

평가자에게 "이 답변 잘했어?"라는 열린 질문을 던지면 헛소리를 하지만, "①②③ 각각 있는지 체크만 해"라고 좁히면 평가자의 일이 **창작에서 확인으로 바뀌어** 할루시네이션이 급감한다. 이 변환의 품질이 제품 전체 품질을 결정한다.

추가 방어 2겹:
- **근거를 규칙 인용으로**: "②번 미충족: '지연 시 ETA 안내' 규칙 위반"처럼 판단 근거를 명시 → 지어내기 어려워지고 알바에게도 legible하다.
- **초기 human-in-the-loop**: 사장님이 초기 평가 결과 몇 개를 검토·교정해 루브릭을 캘리브레이션한다.

손님 역할의 할루시네이션은 무해하다(손님이 사실을 지어내도 훈련 소재). 위험은 전부 평가자에 몰려 있고, 위 3겹으로 방어한다.

### 5-3. 입력 흐름: AI 초안 + 사장님 승인 (완전 자동화 아님)

```
업종 선택 → AI가 업종 템플릿(질문 세트) 제시 → 사장님이 자연어/사진으로 답 채움
        → AI가 루브릭·시나리오 초안 생성 → 사장님 승인/수정 → 확정
```

- AI가 규칙을 통째로 지어내면(완전 자동화) "이 매장 기준"이 아니라 "AI가 상상한 일반 기준"이 되어 차별점이 증발한다. 그래서 **AI는 생성, 사장님은 승인**.
- AI가 알아야 할 것은 "카페엔 이런 상황·항목이 있다"는 **업종 상식**까지다. "스타벅스는 환불이 이렇다"는 **브랜드 정책은 알면 안 된다** (우리 고객은 동네 사장님이고, 그 규칙은 사장님 머릿속에만 있으며, AI가 지어내면 할루시네이션이 된다).
- 브랜드마다 규칙이 다른 문제는 AI 지식이 아니라 **업종 템플릿(AI가 질문을 깔고, 사장님이 답을 채운다)**으로 푼다.

### 5-4. 모달리티: 텍스트 턴제 채팅 (음성은 v2)

훈련에는 "무슨 내용을 말하나(지식)"와 "어떤 톤으로 말하나(전달력)" 두 층이 있는데, 신입이 첫날 못 하는 건 압도적으로 전자다. 텍스트로 내용을 먼저 잡는 게 학습 순서상 맞다. 음성은 STT가 새 할루시네이션 소스가 되어 평가 신뢰성을 흔들기 때문에 v1에서 제외한다. 형식은 녹음 후 제출이 아니라 **턴제 실시간 채팅**(손님 한 마디 → 알바 답변 → 즉시 평가 → 다음 턴)이다. 한 마디마다 교정받는 것이 학습 효과가 가장 좋다.

### 5-5. 데이터 모델 (요지)

- **설정 데이터**(사장님): 규칙, 루브릭, 시나리오 — 매장 링크 단위로 저장(로그인 없이 재사용 성립).
- **훈련 세션 데이터**(알바): 대화 로그, 답변, 피드백, 통과/실패, 재시도 횟수 — 리포트의 재료.
- **루브릭**: 규칙을 채점 가능한 형태로 변환한 데이터. 제품 품질의 핵심.

### 5-6. 기술 스택

- 프론트: React
- 백엔드: Express
- AI 로직: 순수 API 호출로 먼저 구현(안정성 우선) → 여유 시 리팩터링
- 개발 도구: Claude Code 등 AI 코딩 도구 활용
- 평가자 출력: **반드시 JSON 구조**(`{충족여부, 빠진기준[], 피드백, 개선문장}`)로 강제, 마크다운·서두 없이

## 6. 화면 구성 (5개)

| 화면 | 사용자 | 힘 배분 | 핵심 |
|---|---|---|---|
| 규칙 입력 + 루브릭 승인 | 사장님 | ★ 최우선 | 자연어/사진 입력 → 루브릭 변환본 확인·수정 |
| 시나리오 선택 | 알바 | 얇게 | 지연·품절·규칙위반 카드 |
| 훈련 대화 | 알바 | ★ 최우선 | 턴제 채팅 + 인라인 체크리스트 피드백(✓/✗ 항목별) |
| 훈련 결과 | 알바 | 중간 | 통과·재시도·자주 놓친 기준 |
| 결과 확인 | 사장님 | 중간 | 알바별 훈련·약점 리포트 (리텐션 직결) |

4주 안에 정말 잘 만들 것은 **규칙 입력(+루브릭 승인)**과 **훈련 대화** 둘이다. 나머지는 얇게 간다.

### 시나리오 예시 (카페, 3개)

1. **음료 지연** → 사과 / 예상 대기시간 안내 체크
2. **품절 메뉴** → 사과 / 대체 메뉴 제시 / 환불 안내 체크
3. **매장 규칙 위반 손님** → 규칙 안내 / 부드러운 대안 제시 체크

## 7. 로드맵

| 단계 | 범위 | 근거 |
|---|---|---|
| **v1** | 텍스트 대화(A) + 루브릭 평가(B) 코어 | 이 한 쌍을 정확하게 만드는 데 4주 집중 |
| **v1.5** | 매뉴얼 사진 → 규칙 초안 (OCR/비전) | 입력 마찰 제거 최우선 후보. 자연어 입력에 "사진" 갈래를 더하는 것이라 코어 안 흔듦 |
| **v2** | 음성 톤 훈련 | 내용 훈련이 검증된 뒤 별도 축으로 |
| **제외** | 정답 영상 제시 | "받아 적기"라 능동적 교정이라는 제품 철학에 어긋남 + 기술 무거움. 필요 시 "모범 답안 텍스트"로 대체(이미 B의 개선문장이 일부 커버) |

MVP는 업종 1개(카페)로 축소한다.

## 8. 남은 검증 과제

1. **AI 평가 신뢰성**: 정성 피드백보다 체크리스트 기반 정량 평가로 설계(위 5-2).
2. **문제 실재성**: 실제 소상공인/알바 1~2명 인터뷰로 "돈 낼 만한 문제인가" 검증.
3. **비즈니스 모델**: 지불 주체·가격 가설(예: 월 3만 원, 회전율 높은 업종 타깃).
4. **차별화 방어**: 경쟁 비교표(위 1-4)를 발표에서 직접 제시.
5. **핵심 가치 검증**: "사장님 구두 설명 대비 실제로 더 나은가"(직접 해보기 > 듣기 가설) 인터뷰 확인.
6. **타깃 재정의**: 모든 소상공인이 아니라 "회전은 있으나 최소한의 온보딩 여유가 있는" 매장으로 좁힘.
