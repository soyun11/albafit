# checklist.md — 4주 작업 체크리스트

> 매장 맞춤 알바 훈련 서비스 MVP (업종: 카페 1개로 축소)
>
> 쪼갠 3축:
> - **레이어 축**: 데이터·로직(백엔드) / UI(프론트) — 1주차부터 **두 트랙을 병행**하고, 2주차에 mock을 실제 API로 교체하며 합류시킨다. 8개 화면 목업(`ui/1_업종선택.png` ~ `ui/8_사장님리포트.png`)이 이미 나와 있으므로, UI는 로직 완성을 기다리지 않고 1주차에 mock 데이터로 먼저 코딩한다.
> - **중요도 축**: 코어(A 대화 + B 평가)를 먼저, 설정·리포트는 뒤에
> - **완성도 축**: 뼈대(돌아가게) → 정확도(믿을 만하게) → 다듬기(써볼 만하게)
>
> 우선순위 원칙: **(1) 대화+평가 코어 → (2) 규칙 입력 → (3) 리포트(시간 남으면).**
> 가장 어려운 것(규칙→루브릭 변환, 평가 에이전트 신뢰성)을 앞 주차로 당긴다.

---

## 1주차 — 뼈대 & 데이터 + UI 목업 코딩 (두 트랙 병행)

**목표: 트랙 A(백엔드)는 데이터베이스를 만들고, 가장 어려운 "규칙 → 루브릭 변환"이 돌아가게 만든다. 트랙 B(프론트)는 8개 화면을 mock 데이터로 눌러볼 수 있게 만든다. 두 트랙은 따로 진행하되, 데이터 형태(JSON 모양)만 미리 맞춰둔다.**

> DB는 PostgreSQL, 스키마·ERD는 db-schema.md 참고. 아래 6개 테이블(`stores`, `store_rules`, `scenarios`, `rubrics`, `training_sessions`, `session_turns`)을 그대로 가져와 쓴다.

### 트랙 A — 데이터·로직 (백엔드)

#### Day 1 — 프로젝트 셋업 & 배포 대상 만들기
- [ ] 레포 초기화 (React + Express, 프론트/백엔드 디렉터리 분리)
- [ ] `.env` 설계·관리 (Anthropic API 키, `DATABASE_URL`, `.env.example` 커밋)
- [ ] **Railway 프로젝트 생성** — Postgres와 Express 백엔드를 같은 프로젝트에서 호스팅 (plan.md 5-5)
- [ ] **Vercel 프로젝트 생성 및 GitHub 연결** — 프론트(React)용, push마다 자동 배포되는지 확인
- [ ] ORM 셋업 — Prisma 권장 (`npx prisma init`), db-schema.md의 스키마를 `schema.prisma`로 옮기기
- [ ] Anthropic API 연결 스모크 테스트 (키 유효성만 확인하는 최소 호출 1개)
- [ ] 빈 화면·빈 서버 상태로 한 번 배포해보기 — Railway/Vercel 둘 다 "떠 있다"는 것만 확인 (내용은 나중에 채움)

#### Day 2 — 데이터 모델 마이그레이션 & 매장 링크 API
- [ ] 6개 테이블 마이그레이션 실행 (`stores` / `store_rules` / `scenarios` / `rubrics` / `training_sessions` / `session_turns`)
  - [ ] `stores.link_key` UNIQUE 제약 확인 — *로그인 없는 식별의 유일한 키*
  - [ ] `rubrics.approved_at` nullable 확인 — *승인 전 초안 상태를 스키마로 표현*
- [ ] 매장 링크 발급 API: `POST /api/stores` → `link_key` 생성해 반환
- [ ] 매장 조회 API: `GET /api/stores/:linkKey` → 없으면 404
- [ ] Prisma Client로 6개 테이블 CRUD 스모크 테스트 (임의 데이터 삽입·조회 1회씩)
- [ ] **트랙 B와 API 응답 포맷 합의** — 루브릭 `criteria`, 평가 `evaluation` JSON 모양을 이 시점에 확정해 공유 (트랙 B가 만들 mock이 실제 응답과 어긋나면 2주차 교체가 늦어짐)

#### Day 3~4 — 규칙 → 루브릭 변환 (가장 어려운 것, 최우선)
- [ ] **규칙 → 루브릭 변환 LLM 호출** ★ 최난이도 — **Claude Sonnet 5** 사용 (호출 빈도 낮음, 품질 우선. plan.md 5-3)
  - [ ] 프롬프트 설계: "이 매장 규칙을 평가용 체크리스트로 쪼개라. 각 항목 must/nice 구분, 좋은예·나쁜예 포함"
  - [ ] 출력 JSON 스키마 강제: `[{item, required, good_example, bad_example}]` — `rubrics.criteria` 컬럼 형식과 그대로 맞추기
  - [ ] 변환 결과를 `rubrics` 테이블에 저장 (`approved_at = null`인 초안 상태로)
  - [ ] 카페 시나리오 3개(지연·품절·규칙위반)에 대해 손으로 규칙 예시 텍스트를 넣고 루브릭이 뽑히는지 확인
  - [ ] 실패 케이스 1차 점검: 규칙이 모호하거나 짧을 때 루브릭이 비거나 이상해지지 않는지
- [ ] **eval 셋 구축** ★ (규칙 텍스트, 기대 루브릭) 쌍 10~15개를 미리 만들어 저장 — 프롬프트를 바꿀 때마다 감이 아니라 이 셋으로 회귀 확인. 이후 평가 에이전트 신뢰성 검증(2~3주차)에도 같은 방식 재사용
- [ ] 업종 템플릿(질문 세트) 정의 — 카페용: 환불/교환·지연·품절·금지표현 질문 목록 확정
- [ ] 규칙 원문 저장 API: `POST /api/stores/:linkKey/rules` → `store_rules`에 자연어 원문 저장 후 변환 호출 트리거

**트랙 A 1주차 완료 기준**: 규칙을 텍스트로 넣으면 → `store_rules`에 원문이 저장되고 → 변환된 루브릭 JSON이 `rubrics` 테이블에 찍힌다 (DB·콘솔 확인 수준으로 충분, 화면 연결은 2주차).

### 트랙 B — UI (프론트, mock 데이터로 8개 화면 코딩)

- [ ] 화면 라우팅 골격 (사장님 경로 / 알바 경로 분리)
- [ ] 8개 화면을 목업(`ui/1~8_*.png`) 그대로 컴포넌트화 — *제출·연동은 다음 주, 지금은 화면과 이동 흐름만*
  - [ ] 1. 업종선택
  - [ ] 2. 규칙입력 (자연어 textarea + 업종 템플릿 질문 표시)
  - [ ] 3. 루브릭승인 ("이렇게 정리했어요, 맞나요?" + 승인/수정)
  - [ ] 4. 매장링크전달
  - [ ] 5. 시나리오선택 (카드 3개: 지연·품절·규칙위반)
  - [ ] 6. 훈련대화 (턴제 채팅 UI + 인라인 체크리스트 자리)
  - [ ] 7. 훈련결과요약
  - [ ] 8. 사장님리포트
- [ ] 화면별 mock 데이터 fixture 작성 — Day 2에서 트랙 A와 합의한 JSON 포맷 그대로 사용 (예: 루브릭 criteria, 평가 evaluation)
- [ ] 화면 간 라우팅만 연결 (규칙입력→루브릭승인→매장링크전달, 시나리오선택→훈련대화→훈련결과요약) — 실제 제출은 2주차에 연결

**트랙 B 1주차 완료 기준**: 로그인 없이 8개 화면을 순서대로 클릭해 전체 흐름을 mock 데이터로 끝까지 볼 수 있다 (실제 API 연결 없이).

## 2주차 — 코어 로직 완성 + UI mock→실 API 교체

**목표: 알바가 손님 에이전트와 대화하고, 답변이 루브릭으로 채점되어 분기된다. 동시에 1주차에 만든 8개 화면의 mock 데이터를 실제 API 응답으로 교체한다. 제품의 심장.**

### 로직 레이어 — 기능 A (손님 에이전트)
- [ ] **손님 에이전트 대화 LLM 호출**
  - [ ] 시스템 프롬프트: 페르소나 + 시나리오 상태(주문상태·손님기분·경과턴) 주입
  - [ ] **Claude Haiku 4.5** 사용 (호출이 잦으므로 빠르고 저렴한 모델)
  - [ ] 대화 히스토리를 매 호출에 전달 (상태 유지 — LLM은 기억이 없음)
  - [ ] **분기 처리**: 알바 답변에 따라 손님 반응이 달라지게 (1회성 챗봇과 구분되는 지점)

### 로직 레이어 — 기능 B (평가 에이전트)
- [ ] **평가 에이전트 LLM 호출** ★ 신뢰성 핵심
  - [ ] 입력: (루브릭, 시나리오 맥락, 대화 히스토리, 알바 답변)
  - [ ] **Claude Sonnet 5** 사용 (판단이 신중해야 하므로)
  - [ ] **출력 JSON 강제**: `{충족여부, 빠진기준[], 피드백, 개선문장}` — 마크다운·서두 금지
  - [ ] 근거를 규칙 인용으로 대게 ("②번 미충족: 'ETA 안내' 규칙")
- [ ] A와 B를 하나의 턴 루프로 연결 (손님 발화 → 알바 답변 → 평가 → 분기)
- [ ] **미충족 → 재입력 루프**: 개선 문장 제시 후 같은 턴 다시 시도
- [ ] 충족 → 다음 턴 또는 훈련 완료 처리

### 데이터 레이어
- [ ] 훈련 세션 저장 (`training_sessions`/`session_turns`에 대화·답변·평가·재시도 실제 기록 시작)

### UI 연결 — mock → 실 API 교체 (트랙 B 이어서)
- [ ] 규칙입력·루브릭승인 화면(2·3번)을 1주차 변환 API와 연결 (mock 텍스트 대신 실제 제출)
- [ ] 매장링크전달 화면(4번)을 실제 링크 발급 API와 연결
- [ ] 훈련대화 화면(6번)의 mock 대화를 실제 손님 에이전트 API로 교체
- [ ] 훈련대화 화면의 mock 평가 결과를 실제 평가 에이전트 API로 교체

**2주차 완료 기준**: mock이 아니라 실제 API로 알바가 시나리오 하나를 골라 손님과 몇 턴 대화하고, 답변마다 통과/미통과 + 개선문장을 받는다. 화면은 이미 1주차에 만들어져 있으므로 "배선"만 남은 상태.

## 3주차 — 신뢰성 & 디테일 (믿을 만하고 실사용에 안전하게)

**목표: 평가 에이전트가 신뢰할 만해지고, 1~2주차에 붙인 화면들이 목업엔 없던 실사용 엣지 상태(로딩·에러·빈 값)까지 버틴다. 새 화면을 만드는 주차가 아니다.**

### 정확도 (신뢰성)
- [ ] **평가 에이전트 캘리브레이션** ★ (human-in-the-loop)
  - [ ] 사장님이 초기 평가 결과 몇 개를 검토·교정하는 화면/흐름
  - [ ] 오답 케이스 모아 루브릭·프롬프트 다듬기
  - [ ] 엣지 케이스 테스트 (빈 답변, 무관한 답변, 규칙에 없는 얘기)

### UI 디테일 (목업엔 없는 실사용 상태)
- [ ] 훈련대화 화면: 로딩 상태(에이전트 응답 대기 중 표시), 응답 지연 시 처리
- [ ] 훈련대화 화면: 항목별 ✓/✗ 표시가 실제 평가 JSON과 정확히 매핑되는지 (`✓ 사과 / ✗ 대기시간 안내 / ✓ 금지표현 없음`)
- [ ] 루브릭승인 화면: 승인 루프 실동작 확인 (수정 요청 → 재생성 → 다시 승인)
- [ ] 빈 답변·네트워크 오류 등 실패 상태 UI
- [ ] 반응형/모바일 점검 — *알바는 매장 링크를 폰으로 열 가능성이 높음*

**3주차 완료 기준**: 사장님이 규칙 넣고 루브릭 승인 → 링크 전달 → 알바가 대화·교정까지 끊김 없이 흐른다. 평가가 대체로 믿을 만하고, 에러 상황에서도 화면이 깨지지 않는다.

## 4주차 — 리포트 데이터 · MCP 전환 · 배포 · QA

**목표: 전체 흐름을 QA하고, 이미 만들어진 사장님리포트 화면에 실제 데이터를 채우고, 데이터 접근을 MCP로 전환한 뒤 배포한다.**

### 리포트 데이터 채우기
- [ ] 사장님리포트 화면(8번)에 실제 세션 집계 쿼리 연결 (알바별 훈련·약점 리포트) — *화면은 1주차에 이미 있음, 데이터만 채우면 됨*

### MCP 전환 (에이전트–데이터 연결, plan.md 5-6)
- [ ] MCP 서버 프로젝트 셋업, tool 4개 정의 (`get_store_rules`, `get_rubric`, `save_session_turn`, `get_session_report`)
- [ ] 손님 에이전트가 `get_store_rules`·`get_rubric`을 tool call로 쓰도록 교체
- [ ] 평가 에이전트가 `get_rubric`·`save_session_turn`을 tool call로 쓰도록 교체
- [ ] 기존 직접 쿼리 방식과 비교해 정상 동작하는지 회귀 확인 (1주차 eval 셋 재사용)

### 배포 (Day 1에 만든 대상에 실제로 올리기)
- [ ] Express 백엔드 Railway에 배포, 환경변수(`DATABASE_URL`, Anthropic API 키) 프로덕션 값으로 설정
- [ ] React 프론트 Vercel에 배포, 프로덕션 API 주소로 연결
- [ ] 프로덕션 URL로 실제 접속해서 "규칙 입력 → 훈련 → 리포트" 전체 흐름 한 번 확인 (로컬 아닌 배포본 기준)

### QA & 마감
- [ ] 전체 흐름 통합 테스트 (사장님 설정 → 알바 훈련 → 결과 확인)
- [ ] 매장 링크 접속·로그인 없는 경로 점검
- [ ] 발표 시나리오용 데모 데이터(카페 예시) 세팅
- [ ] 경쟁 비교표·문제정의 슬라이드 정리 (plan.md 1-4 활용)

### 여유 시 (시간 부족하면 가장 먼저 버릴 항목)
- [ ] 규칙·시나리오 초안 자동 생성 (업종 템플릿 → AI 초안), AI 초안 승인/수정 UX 다듬기
- [ ] **매뉴얼 사진 → 규칙 초안** — 별도 OCR 서비스 없이 **Claude Sonnet 5의 비전 입력**으로 사진을 바로 읽어 규칙 텍스트를 뽑는다 (plan.md 5-3)

**4주차 완료 기준**: Railway/Vercel에 배포된 URL로 접속해서 "규칙 입력 → 훈련 → 리포트"가 한 번에 보여지는 완결된 v1. 데이터 접근은 MCP로 전환되어 있다.

## 리스크 메모 (막히면 여기부터)
- 루브릭 변환이 부정확 → 1주차에서 막힘. 프롬프트에 좋은예/나쁜예를 더 구체화.
- 평가 에이전트가 오채점 → 2~3주차 핵심 리스크. 루브릭을 더 이분법적으로, 근거 인용 강제, 사장님 캘리브레이션.
- 트랙 A/B 데이터 포맷 불일치 → mock을 만들 때 트랙 A의 JSON 스키마를 반드시 미리 공유(1주차 Day 2). 형식이 어긋나면 2주차 교체가 늦어짐.
- 배포는 4주차에 처음 하지 않는다 → 1주차 Day 1에 빈 껍데기로 미리 올려 파이프라인을 검증해둔다(환경변수·CORS 사고 예방).
- MCP 전환이 늦어짐 → 4주차 핵심 로직은 이미 순수 API로 도는 상태이므로, MCP는 "동작하는 v1 위에 얹는" 순서. 코어(A+B)·배포가 끝나기 전엔 MCP에 손대지 않는다.
- 시간 부족 → **자동화 UX·사진 입력부터 버린다.** 코어(A+B)와 규칙입력은 절대 안 버림.
