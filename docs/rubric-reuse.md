# rubric-reuse.md — 루브릭 재사용성 (기능 강화①)

> `docs/rubric-reset-flow.md`, `docs/auth-improvement-plan.md`와 같은 방식으로 기록한다. 관련 이슈: `soyun11/hub#4`. 근거: `docs/backlog.md` 7절·8절, `docs/checklist.md` 3주차 7/20~7/21 섹션.

## 왜 만들었나

`POST /:linkKey/rules`(`server/src/routes/stores.js`)는 사장님이 규칙을 제출할 때마다 `proposeScenarios()`로 시나리오를 제안받고, 제안된 시나리오마다 `generateRubric()`(`server/src/lib/rubric.js`)으로 Gemini를 호출해 루브릭을 새로 만든다. 업종·규칙이 비슷한 다른 매장이 제출해도 매번 처음부터 호출하므로 비용·시간이 든다. 멘토링 피드백으로 "유사 매장끼리 루브릭 템플릿을 캐싱/공유" 제안이 나왔고, 이번 기능은 그걸 구현한다.

완료 기준(이슈 그대로): **유사한 규칙을 가진 매장이 루브릭을 새로 생성하지 않고 기존 템플릿을 재사용하며, 이 로직에 대한 테스트가 존재한다.**

구현 전 `task-planner` 에이전트로 작업을 쪼개 검토했고, 그 결과 나온 가정 중 두 가지를 사용자가 확정했다 — 아래 "결정" 표에 반영.

## 결정

| 논점 | 결정 | 이유 |
|---|---|---|
| 재사용 판단 단위는? (시나리오 하나하나 vs 배치 전체) | **배치 전체** — `StoreRule` 1건에 딸린 시나리오+루브릭 세트를 통째로 재사용 대상으로 본다 | 시나리오별 세밀 매칭은 4주 챌린지 규모에 비해 복잡도가 과함. 이슈 완료 기준도 "루브릭 재사용"이라고만 하지 시나리오별 세분화까지 요구하지 않는다. 배치 단위여야 `proposeScenarios` 호출까지 같이 아낄 수 있어 "Gemini 호출 자체를 줄임"이라는 원래 취지에도 더 맞는다. |
| 유사도는 어떻게 계산하나? | **임베딩 API 없이, 정규화한 텍스트의 토큰(단어) 집합 overlap(자카드 유사도류)** | 새 외부 의존 추가는 신중해야 한다는 제약(오버엔지니어링 금지) + `docs/backlog.md`가 "임베딩 대체 가능성"을 이미 별도 검토 과제로 분리해둠. 정확도는 낮지만 "매번 새로 생성하는 것보다는 낫다" 수준이면 이번 스코프엔 충분 — 부족하면 별도 과제로 재검토. |
| 재사용 후보 조건은? | **같은 업종(`Store.industry`) + 승인된 루브릭(`Rubric.approvedAt` not null)이 딸린 과거 배치만** | 승인 전 AI 초안을 다른 매장에 퍼뜨리는 건 CLAUDE.md "AI는 생성, 사장님은 승인" 원칙 위반. 사장님이 실제로 검토·승인한 것만 검증된 템플릿으로 취급한다. |
| 재사용해서 만든 새 Rubric의 `approvedAt`은? | **여전히 `null`(승인 전 초안)로 시작** | 템플릿을 그대로 확정 처리하지 않는다 — 이번 매장 사장님이 다시 한번 승인해야 한다는 기존 정책과 동일. 원본이 승인됐다고 복제본까지 자동 승인되지 않는다. |
| 자기 매장의 과거 제출(재설정)도 재사용 후보에 포함하나? | **아니오, 다른 매장 간 재사용만** | 같은 매장의 재설정 흐름은 `docs/rubric-reset-flow.md`가 이미 다루는 별개 문제(규칙 원문 diff 체크는 `docs/ai-usage-and-cost-review.md` 4절 백로그로 분리)라 이번 스코프에서 섞지 않는다. |
| 새 DB 테이블(예: RubricTemplate)이 필요한가? | **아니오** — 기존 `StoreRule`/`Scenario`/`Rubric`을 조회해서 후보를 찾는다 | 4주 챌린지 규모에서 테이블을 늘려 관리 부담을 키울 단계가 아니다. |
| 유사도 threshold 판단 기준은? | **오탐(잘못된 재사용)보다 놓침(재사용 안 하고 새로 생성)이 안전한 방향** — 초기값은 보수적으로(높게) 잡고, 실측 데이터 없이 미세 튜닝하지 않는다 | 재사용을 놓쳐도 기존 흐름(새로 생성)으로 안전하게 폴백되지만, 잘못 재사용하면 안 맞는 채점 기준이 사장님에게 노출된다 — 리스크가 비대칭적이다. |
| 한 배치 안 시나리오 3개 중 일부만 승인됐으면 그 배치를 후보로 볼까? | **아니오 — 배치 안 모든 시나리오의 루브릭이 승인돼야만 그 배치를 후보로 인정** (하나라도 미승인이면 배치 전체를 후보에서 제외) | 배치 단위 재사용으로 정했으므로(위 논점 1) 일부만 복제하면 "배치 전체를 복제한다"는 원칙이 흐려지고, 승인 안 된 시나리오까지 골라내는 부분 복제 로직이 추가로 필요해져 복잡도가 커진다. |

## 다음 단계 (TDD로 순서대로 진행)

`task-planner` 리뷰에서 나온 우선순위 그대로:

1. ~~재사용 스코프 결정 문서화 (이 문서)~~ — 완료
2. 유사도 판단 순수 함수 (`server/src/lib/rubricReuse.js`, 가칭) — 테스트 먼저, `test-writer` 스킬의 단위 테스트 패턴 적용
3. 재사용 후보 선택 순수 함수 (threshold 이상 중 최고점) — 테스트 먼저
4. 재사용 후보 DB 조회 함수 (같은 업종 + 승인된 루브릭만)
5. `POST /:linkKey/rules`에 연결 — 매칭 시 복제, 아니면 기존 흐름 그대로
6. 통합 수동 확인 (매장 2곳으로 실제 재사용 확인, 이후 `feature-verifier`로 검증)

7~9번(라우트 통합 테스트, 엣지 케이스, 로깅)은 "중요"·"여유" 등급이라 시간이 부족하면 가장 먼저 미룬다 — 1~6번만으로 이슈의 완료 기준은 충족된다.

## 구현·검증

### 순수 함수 (`server/src/lib/rubricReuse.js`)
- `normalizeRulesText`/`computeTextSimilarity` — 자카드 유사도 계산. 둘 다 빈 문자열이면 0(오탐 방지).
- `SIMILARITY_THRESHOLD = 0.8` + `findBestReuseCandidate` — threshold 이상 중 최고점 선택.
- `findReuseCandidateBatches({ industry, excludeStoreId })` — 같은 업종 + 자기 매장 제외 + **배치 안 모든 시나리오가 승인된 루브릭을 가진 경우만** 후보로 반환(위 "결정" 표 마지막 항목). 복제에 필요한 시나리오·루브릭 데이터까지 포함해서 반환.
- 테스트 19개(`rubricReuse.test.js`) — 순수 함수는 mock 없이, DB 의존 함수는 `vi.mock('./prisma.js')`로 (`test-writer` 스킬 패턴). 전부 통과, TDD로 테스트 먼저 작성 후 구현.

### 라우트 연결 (`server/src/routes/stores.js`)
`POST /:linkKey/rules`에 3-1단계로 재사용 확인을 추가. 매칭되면 4~5단계(AI 호출)를 건너뛰고 매칭된 배치를 복제, 아니면 기존 흐름 그대로.

전체 서버 테스트(22개) + 루트 lint 통과.

### 통합 검증 (`feature-verifier` 에이전트, 실제 서버·Supabase DB)
- 매장 A(규칙 신규 제출) vs 매장 B(같은 업종, 동일 rawText 제출) 비교: A는 16.79초(Gemini 실호출), B는 0.146초(약 115배 빠름) — AI 미호출의 강한 증거.
- DB 직접 조회: B의 시나리오·루브릭은 A의 row를 참조하지 않는 완전히 새 row(storeId=B)이고, `criteria` 내용은 A의 승인본과 완전히 일치.
- B의 새 Rubric은 4건 전부 `approvedAt: null`로 시작(원본이 승인됐어도 자동 승인 안 됨) — 확인.
- 엣지케이스: 배치 안 시나리오 중 하나라도 미승인이면 그 배치 전체가 후보에서 제외됨을 실제 DB로 확인(부분 승인 배치를 직접 삽입 후 `findReuseCandidateBatches` 호출 → 후보 목록에 없음).
- 엣지케이스: 유사도가 threshold(0.8) 미만이면 `findBestReuseCandidate`가 `null`을 반환함을 확인(재사용 안 하고 기존 흐름으로 폴백).
- **확인 못 한 것**: threshold 미만 텍스트를 실제 라우트(`POST /:linkKey/rules`)로 제출했을 때 정말 기존 AI 생성 흐름을 타는지는 엔드투엔드로 안 함 — Gemini 무료 티어 일일 호출 한도(20회) 절약을 위해 생략, 대신 라우트가 호출하는 동일한 순수 함수 레벨에서 확인(코드 구조상 `null`이면 `if (reuseMatch)` 분기를 안 타고 기존 로직이 그대로 실행됨).
- 버그 발견: 없음.
